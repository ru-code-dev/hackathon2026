# Системные требования · DS-Analyzer

Функциональные и нефункциональные требования к системе в её текущем состоянии.
Каждое требование реализовано и проверено (тесты, оракул, дымовая сборка) — документ
описывает действующие обязательства, а не пожелания.

---

## 1. Границы системы

```
        ВХОДЫ                                 СИСТЕМА                            ВЫХОДЫ
┌─────────────────────┐   ┌───────────────────────────────────────┐   ┌─────────────────────────┐
│ продуктовый проект  │──▶│ ds-analyzer/  (движок, TypeScript)    │──▶│ ui-analyzer/*.json      │
│ (файлы как есть)    │   │  • сканер → правила → метрики → отчёт │   │ ui-analyzer/dashboard.html│
├─────────────────────┤   │  • экстракторы знаний о ките          │   ├─────────────────────────┤
│ чекаут ui-kit-eds-ce│──▶│  • сборка скиллов                     │──▶│ artifacts/*.json (спека) │
│ (только для extract)│   └───────────────────────────────────────┘   ├─────────────────────────┤
├─────────────────────┤                                               │ skills/ (бандл + сценарии)│
│ ds.config.json      │                                               ├─────────────────────────┤
│ (опционально)       │                                               │ POST в Jenkins-вебхук   │
└─────────────────────┘                                               └─────────────────────────┘
```

Вне границ: запуск анализируемого кода, скриншоты/пиксельное сравнение, изменение файлов
проекта кем-либо, кроме `git apply` готового диффа.

## 2. Функциональные требования

### 2.1 Сканирование (FR-SCAN)

- FR-SCAN-1. Обход файлов проекта с семантикой `.gitignore` (включая вложенные) плюс
  исключения из `ds.config.json` и флага `--exclude`; `node_modules` и `ui-analyzer`
  не сканируются никогда.
- FR-SCAN-2. Профилирование без установки зависимостей: имя, менеджер пакетов, монорепо,
  алиасы путей из пяти источников (tsconfig/jsconfig, vite, webpack, package imports,
  `ds.config.json`), принадлежность импортов киту — через транзитивное замыкание его бочек.
- FR-SCAN-3. Сбор наблюдений (`observations@4`): JSX-элементы с пропами и контекстом,
  объявления компонентов, стилевые значения (CSS/SCSS/inline/CSS-in-JS), импорты,
  обработчики событий и клавиш, сообщения встроенного a11y-линта.
- FR-SCAN-4. Двухпроходное разрешение SCSS-переменных; у каждого значения — первопричина
  (deepest declaration) для указания места правки.
- FR-SCAN-5. Всё нечитаемое/неразобранное фиксируется в `limitations` с причиной.

### 2.2 Правила (FR-RULE)

- FR-RULE-1. 26 правил реестра, 32 идентификатора находок в пяти группах:
  токены/стили (9), API кита (5), кастомные компоненты (5), иконки (3), доступность (10).
  Полный перечень с механикой — `features.md`.
- FR-RULE-2. Каждая находка содержит: файл:строка:колонка, фрагмент кода, `actual`,
  `expected` (если известно), «почему», уверенность 0–1, серьёзность, `impactKey`
  (группировка «одно решение»), флаги `autoFixable` / `needsAgent`.
- FR-RULE-3. Автофикс — только замена строки с сохранением числа строк; готовый дифф
  обязан проходить `git apply --check`.
- FR-RULE-4. Правила отключаются по id (`ds.config.json → rules`), отдельные находки
  подавляются по id (`ignoreFindings`).
- FR-RULE-5. Цветовой матчинг — в пространстве OKLab с окном по альфе и ранжированием
  по роли применения; неоднозначные роли не автофиксятся, а помечаются `needsAgent`.

### 2.3 Метрики (FR-METR)

- FR-METR-1. Здоровье 0–100 с опубликованной формулой:
  `round(100 × (0.5 × чистота + 0.3 × внедрение + 0.2 × покрытие токенами))`,
  веса серьёзности error 3 · warning 1 · info 0.25 · candidate 0.
- FR-METR-2. Состав интерфейса: каждый рендеримый компонент ровно в одной из корзин
  (кит / кастом на токенах / смешанный / хардкод / без стилей / внешний), сумма = total;
  проценты замыкаются на 100 методом наибольших остатков.
- FR-METR-3. Токен-вердикт каждого кастомного компонента по его файлу и импортированным
  стилям: tokens / mixed / hardcode / no-styles.

### 2.4 Отчёты (FR-REP)

- FR-REP-1. JSON-артефакты: `findings.json`, `usage.json`, `summary.json`,
  `project-profile.json`, `patches.json` — все проходят zod-валидацию перед записью.
- FR-REP-2. Дашборд — один самодостаточный HTML-файл: без сети, без CDN, подсветка кода
  выполнена заранее (Shiki), payload встроен. Пять экранов — см. `features.md` §3.
- FR-REP-3. PR-конвейер: выбор правок → один unified diff (пересечения объединяются,
  конфликты показываются, ничего не отбрасывается молча) → POST в Jenkins
  generic-webhook-trigger; `repository_url`/`target_branch` определяются из git-чекаута
  проекта; при CORS — эквивалентная curl-команда.

### 2.5 Знания о ките (FR-KIT)

- FR-KIT-1. Шесть артефактов извлекаются автоматически из исходников кита
  (`npm run extract`): tokens (2192), components (61), kit-a11y, kit-icons (233),
  kit-signatures (57), kit-cards (57 + 529 примеров). Ничего рукописного.
- FR-KIT-2. Анализ продукта требует только артефакты — чекаут кита не нужен.
- FR-KIT-3. Отсутствие необязательного артефакта — честная деградация: зависящие правила
  молчат и записывают limitation, а не падают и не выдумывают.

### 2.6 Скиллы Qwen Code (FR-SKILL)

- FR-SKILL-1. Три скилла: `/ds-audit`, `/ds-deep`, `/ds-fix` — сценарии по-русски,
  рассчитанные на слабую модель-исполнителя: команды дословно, у каждого шага маркер
  успеха и одна ветка ошибки; вопросы пользователю — через `ask_user_question`
  с вариантами; ссылки в отчёте — кликабельным markdown.
- FR-SKILL-2. Единый самодостаточный бандл `ds.mjs` (подкоманды `analyze | brief |
  patches | deep-pack | select-patch`); ассеты разрешаются от расположения файла.
- FR-SKILL-3. Установка: `./install.sh` из корня клонированного репозитория
  (или `skills/install-skills.sh` из скопированной папки); `--dir <имя>` — для форков
  Qwen с другим каталогом настроек, пути в сценариях переписываются автоматически.
- FR-SKILL-4. `brief` ≤ ~2 КБ; модель не открывает большие артефакты и не пересчитывает
  числа. `select-patch` строит один общий дифф по union выбранных групп.

## 3. Нефункциональные требования

| ID | Требование | Как проверяется |
|---|---|---|
| NFR-1 | **Детерминизм**: два прогона на одном коде байт-в-байт идентичны | автотест |
| NFR-2 | **Автономность**: у анализируемого проекта не требуется install; у движка нет сетевых обращений во время анализа | дымовой тест без node_modules |
| NFR-3 | **Честность**: непроанализированное перечислено; пустой раздел ≠ «чисто» | оракул сверяет limitations |
| NFR-4 | **Точность**: precision/recall ≥ 0.95 на оракуле; 0 ложных API-срабатываний на 684 примерах кита | оракул-тесты (факт: 1.000/1.000) |
| NFR-5 | **Производительность**: кит целиком (2378 файлов) — единицы минут на ноутбуке | регулярные прогоны |
| NFR-6 | **Среда пользователя скиллов**: только Node ≥ 20 и git; Linux/macOS | дымовой тест бандла; POSIX-sh установщик |
| NFR-7 | **Неразрушающее поведение**: файлы проекта меняет только `git apply`; `push --force` запрещён сценариями | текст SKILL.md, ревью |
| NFR-8 | **Качество кода**: typecheck strict + eslint + prettier + 785 тестов зелёные | `npm run verify` |
| NFR-9 | **Валидность данных**: каждый артефакт проходит zod-схему на записи и чтении | `validateArtifact`, тесты контрактов |
| NFR-10 | **Подсветка кода гарантирована** (чисто-JS движок Shiki, без WASM/сети) | сборка падает, если подсветки нет |
| NFR-11 | **Свежесть поставки**: сборка скиллов падает, если шаблон дашборда старше исходников | проверка mtime в build:skills |

## 4. Требования к средам

| Среда | Требования |
|---|---|
| Пользователь скиллов | Node ≥ 20, git, Qwen Code (или форк); установка копированием |
| Разработчик движка | Node ≥ 20, npm; `npm install` в `ds-analyzer/`; для `extract` — чекаут `ui-kit-eds-ce` рядом или `DS_UI_KIT_ROOT` |
| Анализируемый проект | никаких: файлы читаются как есть |
| CI-канал PR | Jenkins generic-webhook-trigger, POST JSON `{repository_url, branch_name, target_branch, pr_title, pr_body, diff_content}` |

## 5. Известные ограничения

- Статический анализ не видит рантайм: динамически собранные классы и вычисленные пропы
  оцениваются по литеральной части; остальное попадает в limitations.
- Знание пропов кита неполно без установки его апстрима — поэтому скоринг кастомов
  построен так, что отсутствие данных не наказывает (noisy-OR).
- Пороговые значения скоринга откалиброваны на одном эталонном проекте; каждый пойманный
  false positive закреплён юнит-тестом.
- `demo-app` (оракул) намеренно не входит в репозиторий — тесты оракула и дымовая сборка
  требуют его локального присутствия рядом с `ds-analyzer/`.
