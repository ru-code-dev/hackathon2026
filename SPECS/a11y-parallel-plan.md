# A11y-слой параллельно с основной веткой — анализ стыковки

Версия: 1 (анализ, код не писан)
Дата: 2026-07-28
Связанные: [`a11y-research.md`](./a11y-research.md), [`architecture.md`](./architecture.md)

Вопрос: можно ли разрабатывать a11y-слой в отдельной папке, пока другой агент доделывает основной проект. Ответ: **да, примерно 60 % работы — с нулевой координацией.** Ниже — где именно шов, где он ломается и что придётся согласовать.

## 2. Шов: чистый

Архитектура оказалась пригодной для параллельной работы не случайно — правило объявлено как чистая функция:

```ts
// src/rules/types.ts
export interface Rule {
  readonly id: string
  readonly category: FindingCategory
  readonly description: string
  readonly run: (context: RuleContext) => RawFinding[]
}

export interface RuleContext {
  readonly kit: KitSpec
  readonly profile: ProjectProfile
  readonly observations: Observations
  readonly sources: ReadonlyMap<string, readonly string[]>
  readonly spacing: FrequencyIndex
  readonly elementsByFile: ReadonlyMap<string, readonly JsxElement[]>
}
```

Реестр — плоский массив в `rules/index.ts`; `runRules` централизованно навешивает `id`, сниппет и `impact`. Значит **добавление правила = новый файл + одна строка в массиве**. Это настоящая точка расширения, а не случайно получившаяся.

`Declaration` уже несёт то, ради чего a11y-детекция вообще возможна:

```ts
ariaRoles: z.array(z.string()),
ariaAttributes: z.array(z.string()),
nativeTags: z.array(z.string()),
hasInlineSvg: z.boolean(),
```

Это писалось под детектор кастомных компонентов, но `ariaRoles` — ровно тот сигнал, по которому APG-правило понимает «компонент претендует на паттерн».

## 3. Поверхность столкновения — четыре файла

| Файл | Что нужно | Размер правки | Риск |
|---|---|---|---|
| `src/rules/index.ts` | импорт + строки в `RULES` | по строке на правило | минимальный, но конфликт слияния вероятен — файл активно правится |
| `src/domain/findings.ts` | `findingCategorySchema` — **закрытый `z.enum`**, нужен `'a11y'`; плюс опциональные `wcag[]`, `apgPattern`, `a11yImpact` | 1 + 3 строки | низкий, если поля **опциональные** — тогда их код продолжает компилироваться |

Первые три — механика на 10 минут в конце. Четвёртый — единственное, что реально требует согласования.

## 4. Блокер: наблюдения не несут того, что нужно клавиатурным правилам

Это главный результат анализа, и он проверен на схеме и на фикстуре.

**Чего нет в `Observations`:**

1. **Обработчиков событий.** Ни `Declaration`, ни `JsxElement` не фиксируют наличие `onKeyDown` / `onKeyUp`. Проверить «виджет с `role="tablist"` вообще слушает клавиатуру» сейчас нечем.
2. **Литералов клавиш.** `'ArrowRight'`, `'Escape'`, `keyCode` внутри обработчика. `astSignature` объявлен как «identifier-free token stream» — рассчитывать, что строковые литералы там уцелели, нельзя, это не его контракт.
3. **Значений пропов-выражений.** Вот это самое неприятное:

```ts
// src/domain/observations.ts
props: z.record(z.string(), z.string().nullable()),
//                          ^^^ null для пропа, значение которого — выражение
```

А в нашей же фикстуре `demo-app/src/features/settings/SettingsTabs.tsx`:

```tsx
aria-controls={`panel-${item.id}`}   // → props['aria-controls'] === null
id={`panel-${item.id}`}              // → null
```

Значит **проверка ARIA-связей** («указывает ли `aria-controls` на существующий `id`») на текущих наблюдениях неисполнима ровно на том кейсе, ради которого затевалась. Наличие атрибута видно, целостность связи — нет.

**Последствие для планирования.** Из трёх APG-правил:

| Правило | Хватает текущих наблюдений? |
|---|---|
| `a11y.pattern.relations` — атрибут вообще присутствует | ✅ да, `ariaAttributes` |
| `a11y.pattern.relations` — связь целостна (id ↔ aria-controls) | ❌ нет, нужны значения выражений |
| `a11y.pattern.keyboard` | ❌ нет, нужны обработчики и литералы клавиш |
| `a11y.pattern.focus` | ❌ нет, то же |

**Правильный ход:** сформулировать расширение схемы **как аддитивные необязательные поля** и передать другому агенту как отдельный маленький запрос. Опциональность критична — их код продолжает компилироваться и проходить тесты, пока коллектор не дописан, а мы кодируем правила против согласованной схемы, не дожидаясь реализации.

Предлагаемое расширение (в `declarationSchema` и/или `jsxElementSchema`):

```ts
/** Имена обработчиков событий на элементе: ['onClick', 'onKeyDown']. */
eventHandlers: z.array(z.string()).optional(),
/** Литералы клавиш, встреченные в теле обработчиков: ['ArrowRight', 'Escape']. */
keysHandled: z.array(z.string()).optional(),
/** Значения id / aria-* даже когда они собраны из шаблона: сырой текст выражения. */
propExpressions: z.record(z.string(), z.string()).optional(),
```

Третье поле — не «вычислить значение», а «сохранить текст выражения». Для проверки связи достаточно увидеть, что `id` и `aria-controls` собраны по одному шаблону.

## 5. Что строится с нулевой координацией

Ключевое наблюдение: a11y-работа делится на **производителя артефактов** и **потребителя**. Производитель не касается ничего из написанного.

```
ПРОИЗВОДИТЕЛЬ — отдельная папка, ноль общих файлов   ~60% работы
├── APG-экстрактор        30+ HTML → apg-patterns.json
├── @v-uik-экстрактор     dist/*.js + *.d.ts → kit-a11y.json
├── Движок контраста      чистая функция над цветами
└── Аудит контраста кита  tokens.json → kit-contrast.json
                                 │
                                 ▼
                    ds-analyzer/artifacts/*.json     ← ТОТ ЖЕ КОНТРАКТ,
                                 │                      что у tokens.json
                                 ▼                      и components.json
ПОТРЕБИТЕЛЬ — трогает общие файлы                    ~40% работы
├── src/rules/a11y/*.ts        новые файлы, коллизий нет
├── rules/index.ts             +N строк
├── domain/findings.ts         +4 строки
└── dashboard экран            ← ждать M4
```

Это не изобретение схемы — это **третье применение уже дважды доказанного контракта**. `tokens.json` и `components.json` производятся ровно так же: читают кит, валидируются zod, ложатся в `artifacts/`. Никакой новой архитектуры a11y-слой не требует.

**Что можно начинать немедленно, не спрашивая никого:**

| # | Что | Зависит от | Общих файлов |
|---|---|---|---|
| 1 | `npm i` в ките (см. §6 — безопасно) | — | 0 |
| 2 | APG-экстрактор → `apg-patterns.json` | — | 0 |
| 3 | Экстрактор `kit-a11y.json` из `@v-uik/dist` | 1 | 0 |
| 4 | Движок контраста + аудит токенов кита | — | 0 |
| 5 | Правила `a11y.focus.suppressed`, `a11y.name.missing` | — | только `rules/index.ts` |

Пункты 2–4 — это тир 1 и тир 2 из `a11y-research.md` §10, то есть основная ценность. Пункт 5 пишется в изоляции, вливается одной строкой.

## 6. `npm i` в ките — проверено, безопасно

Опасение: 254 теста основной ветки завязаны на **отсутствие** `node_modules` кита. Три из них проверяют это прямо:

```ts
// src/components/extract.test.ts
expect(artifact.meta.typeCheckerAvailable).toBe(false)
expect(...diagnostics).toContain('external-reexport-unresolved')
expect(...diagnostics).toContain('props-type-not-found')
```

**Но установка сама по себе ничего не меняет**, потому что поведение зашито жёстко, а не выведено из окружения:

```ts
// src/components/project.ts:66,72
skipFileDependencyResolution: true,
noResolve: true,
// src/components/extract.ts:239
typeCheckerAvailable: false,
```

`noResolve: true` означает, что TypeScript не пойдёт по импортам, даже если зависимости на месте. Плюс `node_modules` в жёстком списке игнора обходчика.

**Вердикт:** `npm i` инертен для существующего конвейера. Он ничего не ломает и ничего не улучшает — он лишь делает `@v-uik/dist` доступным **новым** читателям, то есть нашему экстрактору.

Разрушительная часть — это **A2** (снять `noResolve`, задействовать типы). Она правит `src/components/project.ts` и три теста, то есть принадлежит очереди другого агента, а не нашей. Это хорошо: A и A2 разделяются, и выгоду для a11y даёт уже A.

## 7. Риски

**1. В репозитории ноль коммитов.** `git` инициализирован, ветка `master`, но истории нет — `git log` падает с «does not have any commits yet». Следствия:

* `git worktree` недоступен (требует хотя бы один коммит) → изоляции через git **нет**;
* отката нет вообще: два агента пишут в одну ФС без точки возврата.

Это самый серьёзный операционный риск, и он дешевле всего чинится: **сделать базовый коммит до начала параллельной работы.** После него доступны и ветки, и worktree, и нормальное слияние вместо ручного разруливания.

**2. `rules/index.ts` — общий файл, правится активно.** Конфликт слияния почти неизбежен, но он тривиален (соседние строки в массиве). Митигация: вливать правила **одним заходом в конце**, а не по одному.

**3. Дашборд занят.** `dashboard/src/screens/*` пишутся прямо сейчас. Экран «Доступность» трогать нельзя до завершения M4 — иначе гарантированный конфликт в общем каркасе, роутинге и `data.ts`.

**4. Расширение `observations` — не наша зона.** Коллекторы принадлежат M2/M3. Правильный ход — запрос с готовой спецификацией полей (§4), а не самостоятельная правка `collectors/typescript.ts` за спиной у того, кто его писал.

**5. Артефакты — общая директория.** `artifacts/` пишется обоими. Наши файлы новые (`apg-patterns.json`, `kit-a11y.json`, `kit-contrast.json`), так что перезаписи нет, но `extract-all.ts` и `extraction-summary.json` — общие, их трогать в последнюю очередь.

## 8. Предлагаемый порядок

```
СЕЙЧАС, без согласования
  0. базовый коммит                              ← до всего остального
  1. npm i в ките                                инертно, проверено
  2. отдельная папка: APG-экстрактор             → apg-patterns.json
  3. отдельная папка: @v-uik → kit-a11y.json
  4. отдельная папка: контраст                   → kit-contrast.json
  5. правила focus.suppressed / name.missing     изолированные файлы

ОТПРАВИТЬ ДРУГОМУ АГЕНТУ ОДНИМ ЗАПРОСОМ
  — три опциональных поля в observations (§4)
  — 'a11y' в findingCategorySchema
  — опциональные wcag[] / apgPattern / a11yImpact в Finding

ПОСЛЕ M4, коротким окном слияния
  6. APG-правила поверх расширенных наблюдений
  7. регистрация всех правил в rules/index.ts    один заход
  8. экран «Доступность» в дашборде
```

Пункты 1–5 не пересекаются с чужой работой ни одним файлом. Пункты 6–8 — короткое окно, когда основная ветка стабилизируется.

**Что важно не делать:** не трогать `src/components/*` (это A2, чужая очередь), `dashboard/src/*` (занято), `scanner/collectors/*` (чужая зона).
