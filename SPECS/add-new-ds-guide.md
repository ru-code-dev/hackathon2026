# Как подключить другую дизайн-систему · руководство по адаптеру

Движок анализа **кит-агностичен**: правила, метрики, дашборд и скиллы ничего не знают
про `sds-eng`. Всё знание о конкретной дизайн-системе живёт в шести JSON-артефактах.
«Адаптер» под новый UI-кит — это способ произвести такие артефакты (плюс имена пакетов
кита). Код правил при этом **не меняется**.

```
                         ГРАНИЦА АДАПТЕРА
                                │
  ваш UI-кит ──▶ экстракторы ───┼──▶ artifacts/*.json ──▶ движок (правила, метрики,
  (исходники)    (пишете вы     │    (контракты в           дашборд, скиллы —
                  или руками)   │     src/domain/)          БЕЗ ИЗМЕНЕНИЙ)
                                │
   меняется ◀───────────────────┴───────────────────▶ не меняется
```

---

## 1. Контракт: шесть артефактов

Схемы — единственный источник истины — лежат в `ds-analyzer/src/domain/`
(`tokens.ts`, `components.ts`, `kit-a11y.ts`, `kit-icons.ts`, `kit-knowledge.ts`);
валидация — `validateArtifact` (zod). Версии зашиты в поле `$schema` (`…@1`).

| Артефакт | Обязательность | Что без него |
|---|---|---|
| `tokens.json` | **обязателен** | не работают правила токенов — теряется главное |
| `components.json` | **обязателен** | не работают API-правила и знания о компонентах |
| `kit-a11y.json` | опционален | a11y-паттерны кита не распознаются; правила честно молчат |
| `kit-icons.json` | опционален | правила иконок пишут limitation вместо вердиктов |
| `kit-signatures.json` | опционален | скоринг кастомов не находит кандидатов |
| `kit-cards.json` | опционален | `/ds-deep` не собирает пакеты для ИИ |

Опциональные слои деградируют честно: фасады `A11ySpec` / `IconSpec` / `KnowledgeSpec`
имеют состояние «недоступен», при котором зависящие правила молчат и записывают
limitation — ничего не падает и не выдумывается.

## 2. Два пути к артефактам

**Путь А — свои экстракторы** (правильный для живого кита). Скопируйте подход
`src/tokens/`, `src/components/`, `src/icons/`, `src/kit-knowledge/`: они читают исходники
кита **тем же коллектором, что и продуктовый код** (`scanProject`), поэтому обе стороны
описаны одним словарём. Кит-специфичные места сосредоточены в `src/config.ts`
(`resolvePaths`: где лежат темы/компоненты/бочки) — под другой кит меняется он и разбор
формата токенов.

**Путь Б — генерация из готовых данных** (быстрый старт). Если у системы уже есть
design-tokens JSON / Figma-экспорт / Style Dictionary — напишите однократный скрипт,
маппящий их в наши схемы. Для `components.json` минимум извлекается из `.d.ts` пакета.

## 3. Пошагово

### Шаг 0 · Имена пакетов

Всё, что импортируется из этих пакетов, движок считает «китом»:
`analyze --kit-package @company/ds` или `ds.config.json → kitPackages`. Транзитивное
замыкание бочек построится само.

### Шаг 1 · `tokens.json` (обязательный)

На каждый токен: стабильный `id`, уровень **ref / sys / comp** (референсные палитры /
семантические роли / компонентные), категория (color/dimension/typography/shadow…),
значение по режимам (light/dark — если есть), CSS-переменная (и общий
`cssVariablePrefix`), для размеров — принадлежность шкале.

На что опирается движок:

- **ранжирование замены цвета по ролям** — у sys-токенов осмысленные имена ролей
  (Background/Text/Border/…): литерал на `background` получит фоновую роль;
- **правило `token.tier.violation`** — различение ref/sys;
- **шкалы** — вердикты «на шкале / мимо шкалы» для размеров;
- точное совпадение цвета ищется в OKLab — значения задавайте точно, конверсию движок
  сделает сам.

Минимально жизнеспособно: ref-палитра + sys-роли с CSS-переменными.

### Шаг 2 · `components.json` (обязательный)

На каждый публичный компонент: имя, экспорт-путь (публичная точка входа — по ней
работают `import.bypass`/`import.internal`), пропы с типами и **вариантами значений**
(питает `prop.invalid`), слоты (приватные помечайте `@inner` — питает
`style.override.inner`), `deprecated`-пометки, `wraps` (какую библиотеку оборачивает).

### Шаг 3 · опциональные слои

- `kit-icons.json` — прогоните `src/icons/extract.ts` по каталогу SVG: фингерпринт
  посчитается сам. Нужны только исходные SVG-файлы набора.
- `kit-a11y.json` — ARIA-паттерны компонентов (роли, атрибуты, клавиши). Если кит
  оборачивает стороннюю библиотеку — как у нас: probe-install апстрима и снятие
  паттернов с него.
- `kit-signatures.json` + `kit-cards.json` — генерируются готовым экстрактором
  `src/kit-knowledge/` из исходников кита + `components.json` (+ `kit-a11y.json`);
  словарь синонимов (`Modal ≈ Dialog ≈ Popup`) — единственное, что стоит пополнить
  под словарь вашей экосистемы.

### Шаг 4 · Прогон

```bash
npm run analyze -- /path/to/project --artifacts /path/to/my-ds-artifacts \
                   --kit-package @company/ds
```

Артефакты валидируются схемами на загрузке — расхождение с контрактом упадёт сразу
и по имени поля.

### Шаг 5 · Калибровка и приёмка (не пропускайте)

1. **Мини-оракул.** Соберите маленький проект с заранее известными нарушениями
   (образец — наш локальный эталон `demo-app/fixtures/expected-findings.json`, разметка ДО прогона; в репозиторий он намеренно не входит).
   Сверьте precision/recall — у нас порог 0.95.
2. **Ноль ложных срабатываний на самом ките.** Прогоните анализатор по каноническим
   примерам вашей ДС: API-правила обязаны молчать.
3. **Детерминизм.** Два прогона — байт-в-байт (`extract` и `analyze` обязаны быть
   воспроизводимыми; никаких Math.random/Date в экстракторах).
4. **Скоринг кастомов.** Пороги (custom ≥ 0.6, ambiguous 0.3–0.6, duplicate ≥ 0.8)
   калиброваны на нашем эталоне; проверьте на своём и закрепляйте каждый пойманный
   false positive юнит-тестом — как сделано в `src/rules/components/score.test.ts`.

### Шаг 6 · Поставка скиллов под вашу ДС

```bash
npm run build:skills
```

Бандл заберёт артефакты из `ds-analyzer/artifacts/` (положите туда свои) и шаблон
дашборда, прогонит дымовой тест и соберёт `skills/`. Тексты `qwen-skills/*/SKILL.md`
от кита не зависят.

## 4. Что менять в коде, а что нет

| Слой | Менять? |
|---|---|
| `src/rules/`, `src/metrics/`, `dashboard/`, `src/skill/`, сценарии скиллов | **нет** — кит-агностичны |
| `src/domain/` (схемы) | нет; расширение — только добавлением опциональных полей с bump версии `$schema` |
| `src/config.ts` (пути внутри чекаута кита) | да — под раскладку вашего репозитория |
| `src/tokens/`, `src/components/` (разбор формата) | да — это и есть адаптер |
| `src/kit-knowledge/SYNONYM_GROUPS` | пополнить синонимами вашей экосистемы |

## 5. Подводные камни

- **Пути** в артефактах — POSIX и относительные (никаких абсолютных и `\`).
- **Стабильность id** токенов и имён компонентов: они попадают в `expected`,
  `impactKey` и тексты замен — переименование ломает сравнимость отчётов.
- **Роли цветов**: если у sys-токенов нет осмысленных ролей, автозамена цвета будет
  предлагать ref-токены и чаще помечать `needsAgent` — это ожидаемая деградация.
- **Альфа-канал**: цвета с прозрачностью матчатся в пределах окна по альфе; следите,
  чтобы токены с альфой имели её в значении, а не в комментарии.
- **Неполные пропы** (кит-обёртка над сторонней библиотекой): скоринг это переживает
  (noisy-OR), но `prop.invalid` будет знать только извлечённые варианты — не считайте
  его молчание гарантией.
- **Дубли в самом ките** (у нас: две пары иконок с одинаковой геометрией): экстрактор
  разрешает их детерминированно и пишет альтернативы в note — проверьте свои.
