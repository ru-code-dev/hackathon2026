# План анализатора UI Kit `ui-kit-eds-ce` и детекции отклонений в проектах

> Цель: набор скриптов, которые (1) извлекают спеку из UI Kit — токены, отступы, имена компонентов, варианты;
> (2) анализируют проект, написанный на этом ките — считают использование компонентов, находят отклонения
> (кастомные цвета вместо токенов, кастомные отступы, шрифты) и детектят самописные компоненты с выдачей кусков кода.

---

## 0. Что уже есть в `ui-kit-eds-ce` — это ваша «эталонная спека»

Кит устроен очень удобно для статического анализа, потому что почти всё лежит в типизированных TS-объектах, а не в рантайме:

| Источник | Что оттуда извлекается |
|---|---|
| `packages/theme/src/ref.ts` | **Ref-токены** (примитивы): палитра `pink100…pink1000`, fontFamilies, fontWeights, lineHeights, fontSize, letterSpacing |
| `packages/theme/src/sys.ts` (`sysLight`/`sysDark`) | **Sys-токены** (семантика): `Background.backAccent`, `Foreground.forePrimary`, `Typography.Text.LargeScreen.TextMN` — ссылки вида `{edsRef.fontSize.m}` |
| `packages/theme/src/theme/*.ts` + `comp.ts` | **Comp-токены** — по одному файлу на компонент (`button.ts`, `card.ts`, …), ключи вида `colorBackgroundContainedPrimaryHover` |
| `packages/theme/src/cssVariables.ts` + `packages/base/createCssVariables.ts` | Правило генерации **CSS-переменных**: префикс `--sds-eng-`, путь через `-`, светлая/тёмная тема через `:root[data-theme='dark']` |
| `packages/base/src/components/*` (62 шт.) | Имена компонентов, публичный API |
| `<Component>/interfaces.ts` | Типы пропсов |
| `<Component>/constants.ts` | **Допустимые варианты**: `views = {primary, secondary, negative}`, `sizes = {xs, sm, md}` |
| `<Component>/classes.ts` | Имена **слотов** (`root`, `spinner`, `contentContainer`) — точки, куда чаще всего лезут переопределять стили |
| `<Component>/*.stories.tsx`, `*.mdx` | Эталонные примеры использования (полезно как ground truth для эвристик) |
| `packages/base/src/components/index.ts` | Публичная поверхность API — что вообще разрешено импортировать |

Три важных нюанса, которые повлияют на скрипты:

1. Кит — **обёртка над `@v-uik/*`**. Значит, импорт напрямую из `@v-uik/button` в проекте пользователя — это уже отклонение (обход кита).
2. Токены содержат **ссылки-строки** `'{edsRef.fontSize.m}'` → нужен резолвер ссылок (похожая логика уже есть в `parseTokens.js`).
3. Есть папка `_DNU_ST_` (Do Not Use) — её использование в проекте это отдельный тип нарушения.

## 1. Скрипты-экстракторы (из кита → в машиночитаемую спеку)

Цель — получить один артефакт `ui-kit-spec.json`, от которого работает второй анализатор. Не парсить кит каждый раз.

### 1.1 `extract-tokens`

- Импортировать `light`/`dark` из `@sds-eng/theme` **напрямую в Node** (через `ts-node`/`tsx`) — не парсить AST. Это надёжнее регулярок.
- Рекурсивно сплющить в плоский список: `{ path, cssVar, rawValue, resolvedValue, tier: ref|sys|comp, theme: light|dark }`.
- Резолвить `{edsRef.*}` / `{edsSys.*}` до конечных значений (hex, px, число).
- Построить **обратный индекс**: `значение → [токены]`. Именно он потом даёт ответ «этот хардкод `#ff1f78` — это `edsRef.palette.pink.pink500`».
- Отдельно вытащить: цвета, spacing/padding-шкалу, radius-шкалу, typography-комбо (family+weight+size+lineHeight+letterSpacing как единый кортеж), shadows, breakpoints.

### 1.2 `extract-components`

- **ts-morph / TypeScript Compiler API**, а не Babel: нужно резолвить `export *` через баррели и типы пропсов.
- Пройти по `packages/base/src/components/index.ts` → собрать реестр: имя, путь, публичный/внутренний, `Component.Subcomponent` (`Button.Icon`).
- Из `interfaces.ts` — список пропсов + типы + JSDoc (он на русском, годится для отчёта).
- Из `constants.ts` — enum допустимых значений `view`/`size`.
- Из `classes.ts` — имена слотов.

### 1.3 `extract-fingerprints` (нужно для детекта кастомов, см. §3)

Для каждого компонента кита посчитать «отпечаток»:

- множество имён пропсов (`{open, onClose, title, children}`),
- набор ARIA-ролей и атрибутов из отрендеренной разметки,
- набор нативных тегов внутри,
- какие comp-токены он потребляет.

### 1.4 `extract-source-hashes`

Нормализованные AST-хеши исходников компонентов кита (для детекта копипасты/форков — §3.I).

## 2. Анализатор проекта пользователя — общая архитектура

Пайплайн из независимых «детекторов», каждый выдаёт `Finding` одного формата:

```ts
Finding = {
  type, severity, confidence,
  file, line, column,
  snippet,            // кусок кода — то, что нужно в отчёте
  actual,             // '#3b82f6' / '13px'
  expected,           // ближайший токен, если есть
  suggestion,         // как починить
  detector            // кто нашёл — для отладки эвристик
}
```

Слои:

1. **Resolver** — резолвинг импортов с учётом `tsconfig.paths`, алиасов, баррелей, реэкспортов, `export { Button as Btn }`.
2. **Collectors** — обход AST (JSX/TSX), CSS/SCSS/CSS-modules (postcss), CSS-in-JS (emotion/styled/JSS), Tailwind arbitrary values `[#fff]`.
3. **Detectors** — правила ниже.
4. **Scorer** — агрегация эвристик в confidence.
5. **Reporter** — JSON + HTML-отчёт.

## 3. Детект **кастомных компонентов** — алгоритмы

Ни одна эвристика по отдельности не работает. Нужен **ансамбль с весами**. От простого к сложному.

### A. Import-graph reachability (база, точность высокая)

Строим граф импортов. Каждый JSX-элемент с заглавной буквы резолвим до места объявления:

- объявлен в `@sds-eng/*` → **использование кита** (учитываем в статистику);
- объявлен в самом проекте → **кандидат в кастомы**;
- из `@v-uik/*` напрямую → **обход кита** (отдельный тип нарушения);
- из стороннего пакета (`antd`, `mui`) → **чужая библиотека**, сильный сигнал.

Это даёт список кандидатов. Дальше — их классификация.

### B. Shadow naming / нечёткое совпадение имён

Кандидат называется похоже на компонент кита → почти наверняка замена.

- Нормализация: убрать префиксы/суффиксы `My`, `App`, `Custom`, `Base`, `New`, `V2`, `Ui`, `Common`, `Styled`, `Wrapped`.
- Сравнение: точное совпадение → вес 1.0; Левенштейн/Jaro-Winkler > 0.85 → 0.7; вхождение подстроки (`PrimaryButton` содержит `Button`) → 0.6.
- Дополнительно: **словарь синонимов** (`Modal ≈ Dialog ≈ Popup`, `Notification ≈ Toast ≈ Snackbar`, `Drawer ≈ SidePanel`, `Chip ≈ Pill ≈ Tag`, `Spinner ≈ Loader`, `TextField ≈ Input`). Это даёт больше всего пользы на практике — люди редко называют «как в ките».

### C. Raw DOM primitives (очень результативно, дёшево)

Ищем нативные теги, которые в ките точно имеют компонент:
`<button>`, `<input>`, `<select>`, `<textarea>`, `<table>`, `<dialog>`, `<a>` со стилями, `<ul>` со списочными классами, инлайновый `<svg>` вместо `Icon`.

Фильтр ложных: `<button>` внутри самого дизайн-системного враппера — ок; `<input type="hidden">` — ок.

### D. ARIA / role-эвристика (ловит «руками собранные» сложные компоненты)

Атрибут выдаёт намерение, даже если имя другое:

- `role="tablist" / aria-selected` → самописные `Tabs`
- `role="dialog" / aria-modal` → самописный `Modal`
- `aria-expanded` + анимация высоты → `Accordion`
- `role="tooltip"` → `Tooltip`
- `aria-haspopup="listbox"` → `Select`/`ComboBox`
- `role="progressbar"` → `Slider`/прогресс

### E. Prop-signature similarity

Jaccard/косинус между множеством пропсов кандидата и отпечатками кита (§1.3).
`{open, onClose, title, footer, children}` vs `ModalProps` → 0.8 → «это Modal».

Веса пропсам: редкие имена (`onClose`, `anchorEl`, `placement`) весят больше, чем `children`/`className` — по сути **TF-IDF по именам пропсов**.

### F. Structural / DOM-shape fingerprint

Нормализуем JSX кандидата в дерево тегов+ролей и сравниваем с деревьями компонентов кита (tree edit distance или упрощённо — мультимножество путей `div>div>button`). Медленно, но ловит переписанные с нуля компоненты.

### G. Style fingerprint

Собираем набор CSS-свойств кандидата и сравниваем с comp-токенами кита. Например, элемент с `border-radius` + `padding: 8px 16px` + `background` + `:hover` + `cursor: pointer` + текстовый контент ≈ кнопка. Совпадение по вектору свойств с `theme/button.ts` → сигнал.

### H. Классификация обёрток (отдельно, самое ценное для отчёта)

Кандидат импортирует кит — это не обязательно плохо. Четыре подтипа:

1. **Тонкий алиас** — реэкспорт/`props`-проброс без изменений → ✅ ок.
2. **Обёртка с дефолтами** — фиксирует `view="primary"` → ⚠️ нормально, но стоит зафиксировать.
3. **Обёртка с переопределением стилей** — `styled(Button)`, `classes={{root}}`, `className` с своими цветами, `!important`, селекторы `.sds-eng-*`, `:global` → 🔴 это и есть «скрытый кастом», настоящая деградация дизайн-системы.
4. **Форк** — скопировали исходник и правят → см. I.

### I. Clone detection (форки компонентов кита)

- Нормализовать AST (убрать имена переменных, форматирование, комментарии) → **winnowing / MinHash + LSH** по k-граммам токенов.
- Сравнить файлы проекта с хешами исходников кита (§1.4).
- Порог схожести > 0.6 → «файл X — форк компонента Y кита, разошлись в N местах». Диффом показать, что именно изменили — это самая ценная часть отчёта.

### J. Внутрипроектная дедупликация

Тот же MinHash, но проект против самого себя: находим один и тот же кастомный компонент, скопированный в 5 фич. Аргумент «это надо унести в кит».

### K. Layout-примитивы

`<div style={{display:'flex', gap:12}}>` / `.wrapper { display: grid }` вместо `Grid`/`Box`/`Container`. Отдельная категория, много ложных срабатываний — держать в низком severity.

### L. Скоринг и ранжирование

```
score = w_B*nameSim + w_C*rawPrimitive + w_D*ariaRole
      + w_E*propSim  + w_G*styleFp     + w_I*cloneSim
```

Веса подобрать на 2–3 реальных проектах. Выдавать **confidence**, а не бинарный вердикт, и обязательно **сниппет кода ±5 строк**. Ранжировать по `score * частота_использования` — сначала то, что встречается в 40 местах.

### M. Ground truth «на халяву»

В ките есть `*.stories.tsx` и e2e-снапшоты. Стори — это эталонные примеры правильного использования; на них можно калибровать детекторы (они не должны срабатывать на сторях кита) — дешёвый регресс-тест на false positives.

## 4. Детект отклонений по стилям (цвета / отступы / шрифты)

### 4.1 Цвета

1. Собрать все цветовые литералы: hex, `rgb()`, `hsl()`, именованные, `color-mix`, в CSS / inline-`style` / CSS-in-JS / Tailwind `[#...]`.
2. Нормализовать в **OKLCH** (перцептивное пространство — иначе сравнение врёт).
3. Классификация по расстоянию до ближайшего токена:
   - **точное совпадение** → «хардкод, но это токен X» — легко чинится автофиксом, самая массовая категория;
   - **ΔE < 2** → «почти токен X» — визуально неотличимо, скорее всего опечатка/пипетка из Figma;
   - **ΔE < 10** → «своя вариация токена X»;
   - **дальше** → «чужой цвет вне палитры».
4. Отдельно: использование **ref-токена вместо sys-токена** (`edsRef.palette.pink500` вместо `edsSys.Background.backAccent`) — нарушение иерархии, ломает тёмную тему.
5. Отдельно: цвет, у которого нет пары в dark-теме → баг тёмной темы.

### 4.2 Отступы / размеры / радиусы

- Извлечь все числовые значения `padding/margin/gap/border-radius/width/height`.
- Сопоставить со spacing-шкалой кита. Классы: **на шкале** / **хардкод, равный шкале** / **вне шкалы** («магическое число» `13px`, `7px`).
- Полезная метрика: **процент значений вне шкалы** по файлу/фиче — сразу видно, где дизайн-система «поплыла».
- Учитывать `rem`/`em`/`%`/`calc()` — приводить к px при известном root font-size, `calc` с токеном внутри считать частично валидным.

### 4.3 Типографика

- Типографика в ките — **кортеж** `{fontFamily, fontWeight, fontSize, lineHeight, letterSpacing}` (см. `sys.ts`).
- Самое частое отклонение: взяли `fontSize` из токена, а `lineHeight` написали руками → **частичное совпадение кортежа**. Именно это и надо детектить: «совпало 3 из 5 полей с `Typography.Text.LargeScreen.TextMN`, расходится `lineHeight`».
- Любой `font-family`, не входящий в `SB Sans Text / SB Sans Display / SB Sans Mono`-стеки → сразу высокий severity.

### 4.4 Прочие отклонения по ките

- Невалидное значение проп-варианта (`view="danger"`, когда в `constants.ts` только `primary|secondary|negative`) — ловится по типам через TS Compiler API.
- `className` / `style` / `classes` на компоненте кита → переопределение стилей.
- Импорт из `_DNU_ST_` или из внутренних путей `@sds-eng/base/src/...` в обход публичного API.
- Прямой импорт `@v-uik/*`.
- Отсутствие `ThemeProvider` / использование хардкода вместо CSS-переменных `--sds-eng-*`.

## 5. Технические решения, которые стоит заложить сразу

- **ts-morph** для TS/TSX (даёт типы и резолвинг), **postcss** + `postcss-value-parser` для стилей, **culori**/`colorjs.io` для OKLCH.
- Разбор **CSS-in-JS**: находить теговые шаблоны ``styled.div`…` `` / ``css`…` `` или объекты в `createUseStyles` и прогонять их содержимое через тот же CSS-детектор. Значения с интерполяцией `${...}` — резолвить, если это токен, иначе помечать как «динамика, не проверено» (честно, лучше чем молча пропустить).
- Единый **IR-формат** между экстрактором и анализатором → анализатор не зависит от версии кита, спека версионируется.
- **Кеш по хешу файла** — иначе на большом проекте clone detection будет долгим.
- Второй режим вывода — **ESLint-плагин** с теми же правилами: анализ для аудита, ESLint для CI, чтобы новое не наливалось.
- Обязательно **allowlist/ignore** (`// ds-ignore`, конфиг с исключениями) — без этого отчётом не будут пользоваться.

## 6. Где будет больно (стоит знать заранее)

- Динамика: `const C = cond ? Button : MyButton`, HOC, render props, `React.cloneElement` — статикой не берётся. Помечать как «не проанализировано», а не пропускать.
- Обёртки вокруг `@v-uik` внутри самого кита — не считать их кастомами.
- Тонкая грань «легитимный продуктовый компонент» vs «должно было быть из кита»: `<UserProfileCard>` — законный кастом, `<CustomButton>` — нет. Спасает только скоринг + ручной ревью топа.
- Ложные срабатывания по цветам: логотипы, иллюстрации, чарты (у графиков своя палитра) — нужен ignore по путям.

## 7. Порядок реализации (для хакатона)

1. `extract-tokens` + обратный индекс `значение → токен` — фундамент, без него ничего не работает.
2. `extract-components` (имена + пропсы + варианты).
3. Детектор хардкод-цветов и отступов — **самый быстрый видимый результат**, много находок сразу.
4. Import-graph + подсчёт использования компонентов кита (метрика adoption).
5. **Детект кастомов: A + B + C + D** (эти четыре дают ~80% пользы за ~20% усилий).
6. Обёртки/переопределения стилей (H).
7. Clone detection (I) — если останется время, но именно он даёт «вау» в демо.
8. HTML-отчёт со сниппетами.

## 8. Открытый вопрос

На каком стеке написан анализируемый проект — как там пишутся стили (CSS-модули / styled-components / emotion / JSS / Tailwind)?
От этого сильно зависит §4 и детектор H. Если стек разный по проектам — collector'ы делать как плагины с общим интерфейсом.
