# A11y-слой анализатора — исследование и варианты

Версия: 1 (research, решения не приняты)
Дата: 2026-07-28
Связанные документы: [`architecture.md`](./architecture.md), [`specs.md`](./specs.md), [`../to-do.md`](../to-do.md)

Задача: добавить в отчёт анализатора отклонения от гайдов по доступности. Ниже — что есть в мире, что из этого применимо к нашей архитектуре, четыре варианта разной стоимости и рекомендация.

---

## 1. Резюме

**Главный вывод: имеет смысл делать не то, что уже делают `eslint-plugin-jsx-a11y` и `axe-core`.** У них обоих есть общая слепая зона, и именно в неё попадают самые дорогие ошибки доступности — и именно её закрывает наша архитектура, потому что у нас уже есть детектор кастомных компонентов и извлечённая спека кита.

Слепая зона — **поведение**: клавиатурная навигация, управление фокусом, связи между элементами паттерна. Статические линтеры проверяют атрибуты по одному элементу, axe проверяет отрендеренный DOM — ни один не проверяет, что виджет, объявивший себя `role="tablist"`, реагирует на стрелки.

Обе фикстуры, уже лежащие в `demo-app`, проходят `eslint-plugin-jsx-a11y` и `axe-core` **начисто** и при этом нарушают APG:

| Файл | Что нарушено | Ловит jsx-a11y | Ловит axe-core | Ловит APG-проверка |
|---|---|---|---|---|
| `SettingsTabs.tsx` | нет навигации стрелками; `tabpanel` без `aria-labelledby`; нет roving `tabindex` | ✗ | ✗ | ✅ |
| `OrderDialog.tsx` | нет закрытия по `Escape`; нет ловушки фокуса; фокус не возвращается на триггер | ✗ | ✗ | ✅ |

Вторая находка исследования — **контраст считается статически**, без браузера, потому что `tokens.json` уже содержит разрешённые цвета в обеих темах с OKLCH и альфой. Это то, ради чего обычно поднимают Playwright.

Третья, и она меняет план: **доступность кита нам сейчас не видна**. 58 из 61 компонента — обёртки над `@v-uik`, зависимости не установлены. Клавиатурная логика `Tabs` живёт в `@v-uik/tabs`; мы знаем, что она есть, только по тестам кита (`Tabs.test.tsx` жмёт `{ArrowRight}`). Рекомендовать «возьмите компонент кита — он доступен» мы пока можем только на веру.

## 3. Ландшафт: кто что покрывает

```
                    атрибут      структура     ПОВЕДЕНИЕ        контраст
                    одного       документа     (клавиатура,     (цвет)
                    элемента                   фокус, связи)
─────────────────────────────────────────────────────────────────────────
jsx-a11y (41)         ███          ░░░            ░░░              ░░░
axe-core (~100)       ███          ███            ░░░              ███ (нужен DOM)
axe-linter (Deque)    ███          █░░            ░░░              ░░░
APG (30+ паттернов)   ███          ███            ███              ░░░
наш кит + tokens.json ░░░          ░░░            ░░░              ███ (без DOM!)
─────────────────────────────────────────────────────────────────────────
                                                   ↑
                                       здесь никого нет,
                                       и здесь самые дорогие ошибки
```

**Почему поведение не покрыто никем.** `jsx-a11y` смотрит на один JSX-элемент и его атрибуты — у него нет модели «виджет из нескольких элементов». `axe-core` смотрит на статический снимок DOM — он не нажимает клавиши. Проверить клавиатуру можно либо ручным тестированием, либо e2e-тестами, которые пишут единицы.

**Про APG важное.** Это не набор правил, а прозаический гайд — «из коробки» его не подключить. Но исходники устроены единообразно: у каждого паттерна `content/patterns/<slug>/<slug>-pattern.html` с секциями `id="keyboard_interaction"` и `id="wai_aria_roles_states_properties"`, клавиши размечены `<kbd>`. То есть **APG извлекается в JSON ровно тем же приёмом, которым мы уже извлекли токены и компоненты** — разовый экстрактор, версионируемый артефакт, валидация схемой. Это не новая архитектура, это четвёртый экстрактор стадии A.

## 4. Четыре варианта

Не альтернативы — слои. Можно брать по одному.

### Вариант 1 · Базовый a11y-линт `S` — ценность низкая

Правила уровня атрибута: невалидная роль, невалидный `aria-*`, роль без обязательных props, кликабельный `<div>` без клавиатуры, `alt`, `tabindex > 0`. Данные берутся из `aria-query` (MIT, модель ARIA 1.2), логика — портированная из `jsx-a11y`.

**Встраивание:** ноль новых коллекторов. `jsxElements[]` и `declarations[]` уже собираются на шаге 3, правила — чистая функция, как и все остальные.

**Против:** это коммодити. У проекта, который заботится о доступности, `jsx-a11y` уже стоит в ESLint, и мы просто продублируем его вывод второй раз, в другом месте, без интеграции с IDE. Ценность появляется ровно там, где плагина нет — а это ровно те проекты, где и остального не соблюдают.

**Митигация:** B0 и так читает `package.json`. Если `eslint-plugin-jsx-a11y` в зависимостях — уводить эти находки в свёрнутый блок «покрыто вашим линтером», а не показывать наравне. Иначе мы добавляем шум в отчёт, который и без того длинный.

### Вариант 2 · Конформность APG-паттернам `L` — ★ рекомендую

Разовый экстрактор `apg-patterns.json` (стадия A, рядом с `tokens.json`), затем правила поверх.

```jsonc
// artifacts/apg-patterns.json
{
  "tabs": {
    "roles": { "container": "tablist", "item": "tab", "panel": "tabpanel" },
    "requiredRelations": [
      { "on": "tablist", "oneOf": ["aria-label", "aria-labelledby"] },
      { "on": "tab", "require": ["aria-selected", "aria-controls"] },
      { "on": "tabpanel", "require": ["aria-labelledby"] }
    ],
    "keyboard": [
      { "keys": ["ArrowRight", "ArrowLeft"], "required": true,  "on": "tablist" },
      { "keys": ["Home", "End"],             "required": false, "on": "tablist" },
      { "keys": ["Enter", " "],              "required": true,  "on": "tab",
        "condition": "manual-activation" }
    ],
    "focus": { "roving": true },
    "kitEquivalent": "Tabs"
  },
  "dialog-modal": {
    "keyboard": [{ "keys": ["Escape"], "required": true }],
    "focus": { "trap": true, "initial": true, "restoreOnClose": true },
    "kitEquivalent": "Modal"
  }
}
```

**Детекция:** сигналы уже собираются — `declarations[].ariaRoles` есть в схеме наблюдений (`architecture.md` §4.1), потому что нужны детектору кастомных компонентов. Поэтому:

```
declaration объявляет role="tablist" / "dialog" / "menu" / ...
        │
        ▼
  сопоставляем с APG-паттерном  →  «компонент претендует на паттерн tabs»
        │
        ├─ ARIA-связи из requiredRelations присутствуют?     ← дёшево, точно
        ├─ обработчик клавиатуры вообще есть на элементе?    ← дёшево, точно
        ├─ упомянуты требуемые клавиши?                      ← дёшево, приблизительно
        └─ фокус: trap / restore / roving tabindex?          ← дорого, приблизительно
```

Первые две проверки детерминированы и дают `confidence 1.0`. Две последние — эвристики (`grep` по телу обработчика на `'ArrowRight'`, `key === 'Escape'`, `keyCode`). Они дают высокий recall и средний precision, поэтому им ставится `needsAgent: true` и подтверждение уходит в стадию E. Это ровно тот случай, под который слой E и проектировался: дешёвое подозрение детерминированно, дорогое подтверждение — агентом.

**Почему это самый ценный вариант:**

1. **Никто больше этого не делает** — ни бесплатно, ни за деньги.
2. **Ложится на уже написанное.** Не новая подсистема, а второй вопрос к тем же `declarations[]`, по которым уже работает `component.custom`.
3. **Фикстуры уже есть.** `SettingsTabs` и `OrderDialog` писались под детектор кастомов, но оказались готовыми a11y-кейсами. Оракул расширяется без новых файлов.
4. **Замыкает главный аргумент продукта.** Сейчас `component.custom` говорит «есть `Modal`, замените». С APG-слоем: «ваш диалог не закрывается по Escape и не удерживает фокус — `Modal` кита это умеет». Первое — вкусовщина, второе — нарушение WCAG 2.1.2, о котором спрашивают на аудите.

**Ограничение, которое надо назвать вслух:** мы анализируем один компонент, а паттерн часто размазан по нескольким файлам (`<Tabs>` в одном, `<TabPanel>` в другом). Разрешать связи между файлами мы не умеем и в первой версии не будем — вместо этого выдаём `partial` и честно пишем, что проверена только часть паттерна. Молчаливый пропуск здесь читался бы как «всё в порядке».

### Вариант 3 · Контраст по токенам `M` — уникально, ни у кого нет

`tokens.json` уже содержит всё необходимое:

```jsonc
"resolved": { "light": "#2969e3", "dark": "#2a72f8" },
"color": { "light": { "rgba": {...}, "oklch": {...}, "hasAlpha": false } }
```

Контраст WCAG — чистая функция от двух цветов. Браузер нужен только чтобы узнать, **какие два цвета оказались друг на друге**. У нас эта пара часто известна из данных:

**3.1 Аудит самого кита.** Comp-токены именуются по конвенции, и пара выводится из имени:

```
comp.barButton.colorTextLight       #13181bcc   ← альфа 0.8, надо композитить
comp.barButton.colorBackgroundLightHover  #2a72f81f
comp.barButton.colorTextLightDisabled     #13181b47   ← альфа 0.28 — вот здесь и будет провал
```

Прогон по всем comp-токенам × 2 темы × состояния (`normal`/`hover`/`active`/`disabled`) даёт диагностики **о ките** — в ту же категорию, что и `spacing-scale-missing`. Это ценный вход для команды ДС и, отдельно, честный ответ на вопрос «а сам-то кит доступен».

**3.2 Проект.** Там, где литеральные `color` и `background` стоят в одном правиле или в одном компоненте, пара определима — считаем. Где фон приходит из родителя — не считаем и пишем в `limitations[]`.

**Что нужно решить:** альфа-композитинг (`#13181bcc` поверх чего?), крупный текст (порог 3:1 вместо 4.5:1 — нужен `font-size`, а он есть в тех же comp-токенах), и то, что для `disabled` WCAG не требует контраста вовсе — правило должно это знать, иначе выдаст пачку ложных находок.

### Вариант 4 · A11y как обоснование существующих находок `XS` — почти бесплатно

Не новые детекторы, а поле в `Finding` и строка в `why`. Половина уже написанного реестра правил имеет прямое a11y-последствие:

| Существующее правило | A11y-последствие | WCAG |
|---|---|---|
| `component.custom` (кастом вместо кита) | своя реализация почти наверняка без клавиатуры | 2.1.1 |
| `component.fork` | форк отстал от исправлений доступности в ките | — |
| `style.override.important` / `.inner` | сломанный `:focus-visible` — самое частое последствие борьбы со стилями | 2.4.7 |
| `icon.inline-svg` | инлайновый SVG без `aria-label`, у иконки кита он есть | 1.1.1 |
| `token.literal.color` | цвет мимо токена = мимо проверенной на контраст пары | 1.4.3 |
| `token.typography.partial` | руками выставленный `line-height` ломает требование интерлиньяжа ≥ 1.5 | 1.4.12 |
| `prop.invalid` | невалидный `view` → компонент падает в дефолт, теряя состояние | — |

Стоимость — добавить в `Finding` поля `wcag: string[]` и `a11yImpact: string | null`, заполнить их в реестре правил. Эффект — отчёт начинает разговаривать на языке, который понимают за пределами фронтенд-команды.

## 5. Рекомендация

| # | Вариант | Оценка | Уникальность | Когда |
|---|---|---|---|---|
| **4** | A11y-обоснование существующих находок | `XS` | — | сразу, внутри M3 |
| **2** | Конформность APG | `L` | **высокая** | M5, рядом с детектором кастомов |
| **3** | Контраст по токенам | `M` | **высокая** | M5, отдельно от 2 |
| **1** | Базовый a11y-линт | `S` | нет | M5+, последним или никогда |

**Порядок 4 → 2 → 3 → 1.** Обоснование:

* **4 берём сейчас** — это правка схемы и текстов, она дешевле, пока правил ещё нет, чем потом.
* **2 — единственное, что делает продукт уникальным.** Оно же лучше всего ложится на уже написанное: `declarations[].ariaRoles` собираются, фикстуры лежат, слой E спроектирован под ровно такие находки.
* **3 — второе уникальное**, и оно вытаскивает максимум из `tokens.json`, самого дорогого нашего артефакта.
* **1 — коммодити**, но берём тоже: см. ревизию ниже.

> **Ревизия от 2026-07-28 (после проверки реестра).** Исходная формулировка «вариант 1 последним или никогда» была перестраховкой. Детерминированный слой стоит 0 токенов, а дашборд спроектирован под тысячи находок с виртуализацией и фильтрами. Проверять надо **всё, что можем проверить**; различать — не тем, запускать ли детектор, а тем, как показать результат. Единственный настоящий ограничитель — не объём, а **ложные срабатывания**: правило, которое систематически неправо, портит доверие ко всему отчёту, сколько бы полезного рядом ни было. Полный разбор по сложности и пользе — §10.

**Уровни 2 и 3 не должны попасть в MVP (M1–M4).** Приоритет M2–M4 не меняется: детектор паттернов поверх ненадёжного сканера бесполезен ровно так же, как детектор кастомов.

## 6. Последствия для проекта

### 6.1 Новые правила в реестр §5.9

| Правило | Источник | Severity | Fix |
|---|---|---|---|
| `a11y.pattern.relations` — паттерн заявлен, обязательные ARIA-связи отсутствуют | `apg-patterns.json` | error | ✅ |
| `a11y.pattern.keyboard` — паттерн заявлен, требуемые клавиши не обрабатываются | `apg-patterns.json` | error | 🤖 |
| `a11y.pattern.focus` — нет ловушки/возврата фокуса, нет roving `tabindex` | `apg-patterns.json` | error | 🤖 |
| `a11y.aria.invalid` — невалидная роль / атрибут / значение | `aria-query` | error | ✅ |
| `a11y.aria.required` — роль без обязательных props | `aria-query` | error | ⚠ |
| `a11y.semantics.raw` — интерактивный не-интерактивный элемент | `aria-query` | warning | ⚠ |
| `a11y.contrast.pair` — определимая пара ниже AA | `tokens.json` | error | ⚠ |
| `a11y.name.missing` — иконка/кнопка без доступного имени | `icons.json`, kit props | error | ✅ |
| `a11y.focus.suppressed` — `outline: none` без `:focus-visible` | коллектор стилей | error | ✅ |

Плюс диагностики **о ките**: `kit-contrast-below-aa`, `kit-pattern-unverifiable`.

`a11y.focus.suppressed` стоит отметить отдельно: это дешёвое, детерминированное правило с почти нулевым ложным срабатыванием, и оно ловит, вероятно, самое частое реальное нарушение в продуктовом коде. Его можно взять даже без остального a11y-слоя.

### 6.2 Схема `Finding`

```ts
  wcag: string[] | null        // ['1.4.3', '2.1.1'] — критерии успеха
  apgPattern: string | null    // 'tabs' — если находка от APG-слоя
  a11yImpact: string | null    // «пользователь клавиатуры не переключит вкладки»
```

Существующие поля не меняются, `enrichment` переиспользуется как есть.

### 6.3 Дашборд

A11y — **сквозная грань, а не отдельный силос**. Отдельный экран нужен, но он должен резать те же самые находки, а не заводить параллельный список:

* фильтр по `wcag` и по `apgPattern` на существующем экране находок;
* **экран «Доступность»**: сводка по критериям WCAG, разбивка по паттернам, отдельный блок «клавиатура» — он самый убедительный;
* блок **«A11y кита»** рядом с «Пробелами кита» — контраст токенов и то, что мы не смогли проверить.

**Health score не трогать.** Растворять доступность в общем числе — значит её потерять: она не сравнима со стилевыми отклонениями ни по цене нарушения, ни по аудитории. Отдельная ось «A11y» рядом с health, со своей формулой.

## 7. Риски и открытые вопросы

**1. ~~Доступность кита нам не видна~~ — снято, проверено 2026-07-28.**
58 из 61 компонента оборачивают `@v-uik`. Реестр `https://gitverse.ru/api/packages/sbertech/npm/` **доступен без авторизации**, `.npmrc` не требуется — проверено скачиванием `@v-uik/tabs@1.23.0` (12 КБ). В пакете:

* `dist/**/*.d.ts` с JSDoc и маркерами `@inner` → закрывает `props-type-not-found` и 25 нерезолвнутых реэкспортов;
* читаемый (неминифицированный) `dist/esm/Tabs.js` с `ArrowUp/ArrowDown/ArrowLeft/ArrowRight`, `role: 'tab'`, `aria-selected`, `aria-controls`, `aria-orientation`;
* `utils/findFocusableSibling` → управление фокусом реализовано.

→ Открытый вопрос из `to-do.md` «устанавливать ли зависимости кита» **закрыт: устанавливать.** Это самое дешёвое действие с самой высокой отдачей во всём проекте — см. §10, строка A.

Поставки — только `dist/`, исходных `.tsx` нет. Для пропов это не важно (`.d.ts` — то, что нужно ts-morph), для a11y-аудита кита достаточно, но означает, что вердикт строится по скомпилированному коду и должен помечаться `confidence < 1`.

**2. Клавиатура статически проверяется приблизительно.**
«Есть ли `onKeyDown`» — точно. «Обрабатывает ли он `ArrowRight` корректно» — эвристика по телу обработчика. Отсюда: `needsAgent: true`, состязательная проверка на стадии E, и честный `confidence` в карточке. Precision этого правила надо измерить на оракуле до того, как оно попадёт в дефолтный набор.

**3. Дублирование с существующим линтом проекта.**
Определяется в B0 по `package.json`, лечится сворачиванием блока. Но решить надо заранее — иначе первый же реальный проект получит сотню находок, которые у него и так горят в CI.

**4. Паттерн, размазанный по файлам.**
Первая версия проверяет один компонент и помечает результат `partial`. Межфайловое разрешение — отдельная задача, не в этот заход.

**5. Лицензии.**
W3C-материалы (APG, WCAG JSON, ACT) — W3C Software and Document License, требует атрибуции; для извлечённого артефакта достаточно указать источник и дату. `aria-query` — MIT, берём как зависимость спокойно. `axe-core` — MPL-2.0; **как зависимость брать не предлагается**, вся ценность его правил у нас либо недостижима (нужен DOM), либо покрывается вариантами 2–3.

**6. Открытые вопросы**
* Целевой уровень — WCAG 2.1 AA или 2.2 AA? От этого зависит, включать ли `target-size` (2.5.8), а он требует размеров и почти не проверяется статически.
* Тянуть ли WCAG JSON в артефакты ради человекочитаемых названий критериев, или зашить нужные 15–20 строкой.
* Нужен ли отдельный `/ds-a11y`, или это флаг `--a11y` у `ds-audit`.
* Проверять ли на APG-конформность **примеры самого кита** (684 файла) — по аналогии с калибровкой детекторов на нуле находок. Скорее всего даст находки, и это будет полезно.

## 8. Чего делать не стоит

| Не делаем | Почему |
|---|---|
| Тащить `axe-core` и рендерить проект в jsdom | Требует установленных зависимостей проекта и рабочей сборки — прямо противоречит требованию §3bis «переваривать любой проект без настройки». Ломается ровно там, где всё остальное работает |
| Поднимать Playwright и обходить страницы | То же плюс необходимость поднять приложение. Не для инструмента, который должен отрабатывать за 5 секунд |
| Копировать все 41 правило `jsx-a11y` | Половина не про React-код (`html-has-lang`, `iframe-has-title`), а остальное дублирует чужой линтер |
| Пытаться проверить порядок фокуса, экранные дикторы, зум | Статически неразрешимо. Место таким вещам — в блоке ограничений отчёта, с явной формулировкой «требует ручной проверки» |

## 9. Принцип отбора: проверять всё, различать в подаче

Прогон детектора стоит миллисекунды и ноль токенов. Дашборд спроектирован под тысячи находок — виртуализация, фильтры, шесть уровней проваливания. Значит, **вопрос «а вдруг у них уже стоит `jsx-a11y`» не должен решать, запускать ли правило.** Мы не знаем, что стоит у проекта, и узнавать это, чтобы что-то не проверить, — не та экономия.

Настоящий ограничитель другой: **ложные срабатывания**. Правило, которое систематически неправо, обесценивает соседние верные находки — читатель перестаёт верить отчёту целиком. Поэтому фильтр на входе один: `precision` на оракуле. Не «полезно ли это» и не «есть ли это у них уже», а «правы ли мы, когда об этом говорим».

Отсюда политика:

* **запускаем всё**, что даёт `precision ≥ 0.9` на оракуле;
* правила ниже порога — не выкидываем, а переводим в `needsAgent` и подтверждаем на стадии E;
* **дублирование с `jsx-a11y` решается сортировкой, а не отключением**: если плагин найден в `package.json` проекта, соответствующие находки уходят в свёрнутый блок «вероятно, уже в вашем CI» — видны, но не занимают верх ленты;
* всё, что проверить не смогли, — в `limitations[]`, как и везде в проекте.

## 10. Полный разбор: сложность × польза

Оценки: `XS` < 1 ч · `S` 1–3 ч · `M` 3–8 ч · `L` 1–2 дня.
Польза — насколько вырастает ценность отчёта, а не насколько правило «правильное».

### Тир 1 — брать безусловно (лучшее отношение пользы к цене)

| | Что | Сложн. | Польза | Почему именно это |
|---|---|---|---|---|
| **A** | **Установить `@v-uik`** и перезапустить экстракторы | `S` | **макс.** | Одна команда снимает три записанных ограничения разом: `props-type-not-found`, 25 нерезолвнутых реэкспортов, непроверяемая a11y кита. Плюс поднимает точность `prop.invalid` и качество `signatures.json`. Реестр открыт, проверено |
| **A2** | Задействовать типы в экстракторе компонентов (снять `noResolve`) | `M` | **макс.** | Сама установка ничего не даст, пока ts-morph грузится с `noResolve`. Это и есть основная работа пункта A |
| **C** | `a11y.focus.suppressed` — `outline: none` без `:focus-visible` | `XS` | **высокая** | Правило на уже собранных `styleValues[]`, новых данных не нужно. Почти нулевой ложняк, автофикс. Вероятно, самое частое реальное нарушение в продуктовом коде |
| **D** | Поля `wcag[]` / `a11yImpact` в `Finding` + заполнение в реестре | `XS` | **высокая** | Не детектор, а переозначивание: половина существующих правил уже ловит a11y-последствия. Переводит отчёт на язык, понятный вне фронтенда |
| **E** | `a11y.name.missing` — icon-only контрол без доступного имени | `S` | **высокая** | Kit-aware: `Button` с `icon` и без `aria-label`, инлайновый `<svg>` без `title`. Детерминированно, автофиксится, встречается часто |
| **M** | Прогон 684 примеров кита через a11y-правила | `XS` | **средняя** | Инфраструктура калибровки уже запланирована шагом 10. Даёт и калибровку, и бесплатные находки о ките |

**Итого тир 1 ≈ 1.5 дня.** Даёт заметный a11y-раздел без единого нового источника данных.

### Тир 2 — высокая польза, требует новых данных

| | Что | Сложн. | Польза | Комментарий |
|---|---|---|---|---|
| **B** | Экстрактор `kit-a11y.json` из `@v-uik`: по компоненту — роли, `aria-*`, обрабатываемые клавиши, наличие ловушки фокуса | `M` | **высокая** | Зависит от A. Превращает «возьмите компонент кита» из веры в проверенное утверждение. Заодно даёт диагностики о ките. Строится по `dist/`, поэтому вердикт помечается `confidence < 1` |
| **J** | Контраст comp-токенов кита (аудит ДС) | `M` | **высокая** | Уникально: ни один инструмент не считает контраст без браузера, а у нас есть разрешённые цвета обеих тем. Возни требует альфа-композитинг и то, что для `disabled` WCAG контраста не требует |
| **F** | Валидность ARIA по `aria-query`: невалидная роль / атрибут / значение, роль без обязательных props | `S` | **средняя** | Data-driven из спеки ARIA 1.2 → ложняков практически нет. Пересекается с `jsx-a11y`, но по §9 это решается подачей |
| **L** | Экран «Доступность» в дашборде | `M` | **высокая** | Без него всё остальное не видно. Разделы — см. §11 |

**Итого тир 2 ≈ 2.5 дня.**

### Тир 3 — уникально, но дорого

| | Что | Сложн. | Польза | Комментарий |
|---|---|---|---|---|
| **H** | Экстрактор `apg-patterns.json` из 30+ HTML APG | `M` | — | Фундамент для I, сам по себе пользы не даёт |
| **I** | Правила `a11y.pattern.relations` / `.keyboard` / `.focus` | `L` | **очень высокая** | То, чего нет ни у кого. Связи и наличие обработчика — детерминированно; разбор тела обработчика — эвристика с `needsAgent` |
| **K** | Контраст определимых пар в коде проекта | `S` | **средняя** | Дёшево после J, но пар, где оба цвета известны, объективно немного |
| **G** | Поведенческие правила `aria-query`: клик без клавиатуры, интерактивность на неинтерактивном, `tabindex` | `S` | **средняя** | Полезно, но `click-events-have-key-events` известен ложняками — только через оракул |

**Итого тир 3 ≈ 2.5 дня.**

### Не брать

| | Что | Сложн. | Почему нет |
|---|---|---|---|
| **N** | WCAG JSON как артефакт | `XS` | Нужны только человекочитаемые названия 15–20 критериев. Зашить строкой дешевле, чем тянуть и версионировать внешний источник |
| **O** | Landmark / heading structure | `S` | Правила про страницу, а мы анализируем компоненты. Композиция приложения нами не разрешается → систематические ложняки |
| **P** | `axe-core` в jsdom | `L` | Требует установленных зависимостей проекта и рабочей сборки — прямо ломает требование §3bis «любой проект без настройки» |
| **Q** | Playwright / e2e-обход | `XL` | То же плюс поднятие приложения. Не для инструмента, который должен отрабатывать за 5 секунд |

### Если времени мало

* **Только тир 1** — a11y-раздел есть, он честный, стоит полтора дня и не трогает архитектуру.
* **Тир 1 + A/B** — появляется главный аргумент: «кит это умеет, ваша реализация — нет», подкреплённый кодом `@v-uik`.
* **Резать в первую очередь H+I**, а не C/D/E: они самые дорогие, и без надёжного сканера всё равно не взлетят.

## 11. Разделы экрана «Доступность»

Экран режет **те же самые** находки, а не заводит параллельный список.

| Раздел | Содержимое | Откуда |
|---|---|---|
| **Сводка** | Отдельная ось «A11y» (не растворять в health score), счётчики по severity, число затронутых критериев WCAG | все `a11y.*` |
| **Клавиатура** | Самый убедительный раздел: виджеты, недостижимые с клавиатуры; подавленный фокус-ринг; ловушки фокуса | C, I |
| **Паттерны** | По APG-паттернам: заявлен / выполнен контракт / чего не хватает. Рядом — компонент кита, который это уже умеет | I + B |
| **Контраст** | Найденные в проекте пары со swatch'ами и коэффициентом; отдельно — пары, где фон не определим | J, K |
| **Имена и семантика** | Контролы без доступного имени, невалидный ARIA, интерактивность на `<div>` | E, F, G |
| **A11y кита** | Зеркало блока «Пробелы кита»: контраст токенов, что в `@v-uik` не проверилось | J, B |
| **Требует ручной проверки** | Порядок фокуса, дикторы, зум, паттерны, размазанные по файлам | `limitations[]` |

Плюс сквозные фильтры `wcag` и `apgPattern` на обычном экране находок — чтобы к a11y можно было прийти и не заходя на этот экран.
