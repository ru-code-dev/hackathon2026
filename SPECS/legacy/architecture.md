## 1. Принципы

### 1.1 Синтаксис стилей важен ровно в одном месте

Один и тот же хардкод в четырёх синтаксисах:

```scss
.card { background: #ff1f78; }                    /* SCSS-модуль */
```
```ts
styled.div`background: #ff1f78;`                  // CSS-in-JS
```
```tsx
<div style={{ background: '#ff1f78' }}>           // инлайн
```
```tsx
<div className="bg-[#ff1f78]">                    // Tailwind
```

Это **одно и то же нарушение**. Различается только способ добыть строку `background: #ff1f78` и её координаты в файле.

Отсюда главное архитектурное решение: **разделить сбор и анализ**.

```
СБОР (зависит от синтаксиса)          АНАЛИЗ (не зависит ни от чего)
├── scss/css/modules → postcss    ┐
├── styled/emotion   → AST+шаблон ├──►  StyleValue[]  ──►  правила
├── style={{...}}    → AST        │     {property, value, file, line, col}
└── tailwind         → классы     ┘
```

Каждый адаптер — 100–150 строк. Добавить Tailwind = один новый файл, ноль изменений в правилах.

**Целевой стек — SCSS-модули, но CSS-in-JS поддерживается наравне.** Это две реализации одного интерфейса.

### 1.2 Найти ≠ предложить

Два разных решения, которые легко спутать:

| | |
|---|---|
| **Находим** | **всё.** Любой цветовой литерал в коде — наблюдение. Совпал с токеном, почти совпал, вообще чужой — всё попадает в отчёт |
| **Предлагаем** | зависит от того, что вообще есть в ките |

Требование «находить всё, что можно» и политика «предпочитать sys-токены» не конфликтуют: находим все хардкоды, а в поле `after` диффа кладём лучшее из доступного.

### 1.3 ref против sys — почему это не педантизм

```
ref.palette.pink.pink500      светлая #ff1f78    тёмная #ff1f78   ← одинаково
sys.Background.backAccent     светлая #2969e3    тёмная #2a72f8   ← меняется
```

**ref — это краска. sys — это роль.**

`pink500` — «вот такой розовый», он такой всегда. `backAccent` — «фон акцентного элемента», и система сама решает, какой он в текущей теме.

Практическое последствие ровно одно:

```css
/* написали ref */
background: var(--sds-eng-palette-pink-pink500);
/* пользователь переключил тёмную тему → фон остался #ff1f78 */

/* написали sys */
background: var(--sds-eng-Background-backAccent);
/* → фон стал #2a72f8 автоматически */
```

Второе следствие: если бренд поменяет акцентный цвет, sys-токены переедут все разом, а все ref-хардкоды придётся искать руками.

**Почему нельзя сделать «ref всегда ошибка» сплошным правилом.** В ките 1125 цветовых токенов, но семантических ролей на порядок меньше. Не у каждого цвета палитры есть sys-эквивалент. Если дизайнер взял `pink500` для чего-то, чему в системе нет роли, — выразить это через sys физически невозможно. Правило «ref всегда ошибка» породило бы находки, которые нельзя починить, а такой отчёт закрывают на второй раз.

Поэтому правило условное:

```
#ff1f78 найден
   ├─ есть sys-токен с этим значением?  → предлагаем sys, severity error, autoFix ✅
   └─ нет                               → предлагаем ref
                                           + ⚠ «не переключится в тёмной теме»
                                           + отдельный блок дашборда:
                                             «в ките нет семантической роли для этого цвета»
```

Второй случай — это не «мы не смогли», а находка **про сам кит**. Её стоит показывать отдельно: это ценный вход для команды дизайн-системы.

### 1.4 Что считать кастомным компонентом

Вопрос «кастомный ли это компонент?» — философский и неотвечаемый. Правильный вопрос — **«есть ли в ките эквивалент?»**, и он проверяем.

| Компонент | Эквивалент в ките | Вердикт |
|---|---|---|
| `OrderCard` | нет | законный продуктовый компонент, **не находка** |
| `MyButton` | `Button` | находка |
| `OrderDialog` | `Modal` | находка |
| `SettingsTabs` | `Tabs` | находка |

Порог не нужен: скор сопоставления **и есть** ответ. Показываем ранжирование кандидатов с confidence, а не бинарный вердикт.

### 1.5 Пробелы фиксируются, а не замалчиваются

Динамика (`styled.div\`background: ${props => props.color}\``), HOC, render props, файлы без парсинга — помечаются как «не проанализировано» и попадают в отдельный блок отчёта. Молчаливый пропуск читается как «здесь всё чисто», а это ложь.

## 3. Стадия A — спека кита

Считается один раз на версию кита, не пересчитывается при анализе проекта.

### 3.1 Что уже готово

| Артефакт | Содержимое |
|---|---|
| `tokens.json` | 2192 токена (ref 317 · sys 258 · comp 1617), 571 CSS-переменная, 7 шкал, 4 обратных индекса, 6 диагностик |
| `components.json` | 61 компонент (57 публичных), 168 React-компонентов, 132 типа пропов / 373 члена, 38 наборов вариантов, 48 наборов слотов / 246 слотов, 462 публичных символа |

### 3.2 Что добавляем

#### `examples-index.json` — корпус использования

`packages/base/src/components/*/examples/*.tsx` — **684 файла, 60 из 61 компонента, 794 КБ**. Самодостаточные канонические сниппеты с реальными импортами:

```tsx
import { Button } from '@sds-eng/base'

export const FilledButtons = () => (
  <div style={{ display: 'flex', columnGap: 15 }}>
    <Button view="primary">Primary</Button>
    <Button view="secondary">Secondary</Button>
    <Button view="negative">Negative</Button>
  </div>
)
```

Формат записи:

```jsonc
{
  "id": "Button/FilledButtons",
  "component": "Button",
  "code": "…",
  "lines": 9,
  "propsUsed": ["view"],
  "componentsUsed": ["Button"],
  "tags": ["variants"]
}
```

Три применения:

1. **Контекст для агента.** Десять строк примера учат модель использовать `Button` лучше, чем таблица из 40 пропов.
2. **Вывод реального API.** Примеры содержат пропы, которые **не извлекаются из AST**: `color`, `kind`, `view`, `size`, `icon`, `text`, `label`. Типы живут в `@v-uik` и без установленных зависимостей недоступны. `grep` по JSX закрывает диагностику `props-type-not-found`.
3. **Калибровочный корпус.** Прогон анализатора по 684 примерам должен дать **ноль** находок. Детектор, срабатывающий на коде самого кита, откалиброван неверно. Это автотест в CI.

#### `cards.json` — прогрессивное раскрытие

Решение проблемы «описание компонентов огромное». Это **проблема выборки, а не контекста**. Полная спека кита — ~5.5 МБ, но агенту при замене одного компонента нужно знать только:

1. *какие компоненты вообще существуют* — чтобы выбрать кандидатов;
2. *как выглядит правильное использование выбранного* — чтобы написать код.

| Уровень | Что | Размер | Когда в промпте |
|---|---|---|---|
| **T0** — каталог | Имя + назначение одной строкой + сигнатура ключевых пропов | ~50 токенов × 61 = **~3 000 токенов** | Всегда |
| **T1** — карточка | Полные пропы, варианты, слоты, подкомпоненты, 2 примера | ~700 токенов × 5 кандидатов = **~3 500** | Только для отобранных кандидатов |
| **T2** — глубина | Весь `examples/`, `API.mdx`, e2e-снапшот | ~10 000 | Только по явному запросу агента |

**Бюджет одного агентского вызова ≈ 8 000 токенов.** 50 кастомных компонентов = 50 параллельных агентов, каждый видит ровно то, что ему нужно.

```jsonc
{
  "Button": {
    "t0": "Button — кнопка. view: primary|secondary|negative · size: xs|sm|md · kind: ghost · icon · disabled · onClick",
    "t1": {
      "import": "import { Button } from '@sds-eng/base'",
      "props": [ { "name": "view", "values": ["primary","secondary","negative"], "default": "primary" } ],
      "slots": ["spinner", "onlyIcon", "contentContainer"],
      "subcomponents": ["Button.Icon"],
      "wraps": "@v-uik/button",
      "examples": ["Button/FilledButtons", "Button/DifferentSizeButtons"]
    }
  }
}
```

Строка `t0` собирается механически из `components.json` и **пополняется пропами, вычисленными из примеров**.

#### `signatures.json` — отпечатки для сопоставления

```jsonc
{
  "Modal": {
    "propSignature": ["open", "onClose", "title", "footer", "children"],
    "propWeights": { "onClose": 3.1, "open": 2.4, "children": 0.2 },
    "ariaRoles": ["dialog"],
    "domShape": ["div>div>header", "div>div>footer"],
    "synonyms": ["Dialog", "Popup", "Overlay", "Lightbox"],
    "nativeEquivalents": ["dialog"]
  }
}
```

Веса пропов — **TF-IDF по всему киту**: `onClose` встречается у трёх компонентов и потому информативен; `children` — у всех и потому бесполезен. Именно это делает ранжирование кандидатов осмысленным.

#### `icons.json` — 466 иконок

`packages/base/src/icons/svg/` содержит 466 SVG. Извлекаем имя, размерный вариант, `viewBox`, нормализованный хеш `path`-данных. Позволяет вместо «здесь инлайновый SVG» сказать «это ровно `io16-Default`, замените на компонент кита».

## 3bis. Стадия B0 — профилирование проекта

**Требование: сканер обязан переваривать любой React/TypeScript-проект без настройки.** Никаких допущений про `src/`, про структуру папок, про фреймворк, про то, установлены ли зависимости.

Поэтому перед сбором идёт отдельная стадия — разведка. Она отвечает на вопросы «где я и как здесь всё устроено», и её результат — единственное, что знает о конкретном проекте.

```
                          вход: путь (файл | папка | корень репо)
                                        │
                    ╔═══════════════════▼════════════════════╗
                    ║           B0 · ПРОФИЛИРОВАНИЕ          ║
                    ╚═══════════════════╤════════════════════╝
                                        │
        ┌───────────────┬───────────────┼───────────────┬────────────────┐
        ▼               ▼               ▼               ▼                ▼
  найти корень    собрать все     собрать все     прочитать      определить,
  (package.json   tsconfig/       алиасы         .gitignore     как импортируется
   или .git,      jsconfig        из 5 источн.   + дефолты      кит именно здесь
   вверх от пути) (все в монорепе)                              (не угадывать!)
        │               │               │               │                │
        └───────────────┴───────────────┴───────┬───────┴────────────────┘
                                                │
                                                ▼
                                    project-profile.json
```

### 3bis.1 Что мы НЕ предполагаем

| Допущение, которого нет | Как обрабатывается |
|---|---|
| Есть папка `src/` | Обходим от переданного пути. Может быть `app/`, `packages/*/src`, `lib/`, корень |
| Один `tsconfig.json` | Собираем все, привязываем каждый файл к ближайшему вверх по дереву |
| Алиасы объявлены в tsconfig | Читаем 5 источников, см. ниже |
| Зависимости установлены | Не требуются. Резолвинг — синтаксический, `node_modules` только опциональный источник |
| Проект собирается | Не требуется. Ошибка типов не мешает разбору AST |
| Расширения `.ts`/`.tsx` | `.ts .tsx .js .jsx .mts .cts .mjs .cjs` |
| Стили только в `.scss` | `.css .scss .sass .less .styl` + любые `.module.*` |
| Конкретный фреймворк | Next.js, Vite, CRA, Remix, Astro, монорепа — для нас это просто файлы |
| Кит импортируется как `@sds-eng/*` | Определяем фактический способ, см. 3bis.4 |
| Проект вообще использует кит | Если не использует — говорим об этом прямо, а не рисуем health 100 |

### 3bis.2 Определение области сканирования

```
вход = путь
   │
   ├─ файл?    → сканируем один файл, корень ищем вверх по дереву
   ├─ папка?   → сканируем поддерево, корень ищем вверх по дереву
   └─ ничего?  → сканируем cwd
                       │
                       ▼
          корень = ближайший вверх каталог с package.json,
                   иначе с .git, иначе сам путь
                       │
                       ▼
          исключения (в порядке применения):
            1. всегда:   node_modules, .git, dist, build, out,
                         .next, .nuxt, .turbo, .cache, coverage,
                         storybook-static, *.min.*, *.d.ts
            2. .gitignore проекта (все, включая вложенные)
            3. .dsignore проекта, если есть
            4. --exclude из командной строки
```

Обход — по расширениям, а не по ожидаемым именам папок. Симлинки не разыменовываются (защита от циклов в монорепах).

### 3bis.3 Разрешение алиасов — пять источников

Алиасы — главный источник хрупкости. `import { Button } from '@/shared/ui'` не разрешится, если не знать, куда указывает `@/`.

Читаем в порядке приоритета, объединяя:

| # | Источник | Что берём |
|---|---|---|
| 1 | `tsconfig.json` / `jsconfig.json` | `compilerOptions.baseUrl` + `paths`, с раскруткой `extends` |
| 2 | `vite.config.*` | `resolve.alias` — статический разбор AST, без выполнения конфига |
| 3 | `webpack.config.*` / `craco.config.*` | `resolve.alias` — то же |
| 4 | `package.json` | `imports` (subpath imports вида `#internal/*`) |
| 5 | `next.config.*`, `.babelrc` (`module-resolver`) | по возможности |

Конфиги **не выполняются** — только статический разбор. Выполнение чужого конфига и небезопасно, и требует установленных зависимостей.

Дальше — обычный порядок резолвинга: относительный путь → алиас → `node_modules` (если есть) → внешний пакет.

Неразрешённый импорт **не ошибка**: он записывается как `unresolved` и попадает в блок ограничений отчёта.

### 3bis.4 Определение кита — не угадывать, а найти

Наивно искать `@sds-eng/*`. В реальности кит попадает в код тремя путями:

```
1. прямой импорт
   import { Button } from '@sds-eng/base'

2. через алиас или воркспейс монорепы
   import { Button } from '@company/design-system'
   import { Button } from '~/packages/ui'

3. через собственную ре-экспортную бочку проекта
   // src/shared/ui/index.ts
   export { Button, Modal } from '@sds-eng/base'
   // и дальше везде:
   import { Button } from '@/shared/ui'
```

Третий случай самый частый и самый коварный: если его не учесть, анализатор решит, что проект вообще не использует кит.

Алгоритм:

```
1. базовый список паттернов кита:  @sds-eng/*, @v-uik/*
                                   (+ --kit-package из CLI, + ds.config.json)

2. просканировать ВСЕ импорты проекта
   └─ найти локальные модули, которые ре-экспортируют кит
      export * from '@sds-eng/base'   → этот модуль тоже «кит»
      export { Button } from '@sds-eng/base'

3. повторить, пока множество не перестанет расти
   (транзитивное замыкание, обычно 2–3 итерации)

4. итог: множество «китовых» источников
   { '@sds-eng/base', '@/shared/ui', 'src/ui/kit' }

5. если множество пусто и в package.json нет зависимости на кит
   → отчёт: «проект не использует sds-eng», а не health 100
```

Транзитивное замыкание нужно, потому что бочки бывают многоуровневыми: `@/shared/ui` → `@/shared/ui/base` → `@sds-eng/base`.

### 4.2 Матрица поддержки синтаксисов

| Синтаксис | Парсер | Статус | Ограничение |
|---|---|---|---|
| `*.css`, `*.module.css` | `postcss` | полная | — |
| `*.scss`, `*.module.scss` | `postcss-scss` | полная | SCSS-переменные и `@mixin` требуют разрешения, см. ниже |
| `styled-components` | `ts-morph` + разбор тега | полная | интерполяции `${fn}` — динамика |
| `emotion` (`css``/`styled``/`css={}`) | то же | полная | то же |
| `style={{ … }}` | `ts-morph`, объектный литерал | полная | вычисляемые значения — динамика |
| JSS / `createUseStyles` | `ts-morph`, объектный литерал | полная | то же |
| Tailwind | классы + arbitrary `[#fff]` | плагин | включается опцией |
| CSS Modules `composes` | `postcss` | частичная | цепочки между файлами разрешаются на 1 уровень |

#### SCSS-переменные — как разрешаются

```scss
$brand: #ff1f78;              ← объявление
.card { color: $brand; }      ← использование
```

Наивный `postcss-scss` увидит `$brand` и не поймёт, что это `#ff1f78`. Компиляция через `sass` даст значение, но потеряет координаты в исходнике — а нам нужно показать дифф на исходной строке.

Решение — **два прохода**:

1. `postcss-scss` по исходнику → координаты + сырые значения (`$brand`)
2. Разрешение простых цепочек: `$brand` → `#ff1f78`, `map-get($colors, brand)` → значение
3. Находка репортится на строке `.card { color: $brand }`, **но дополнительно помечает объявление** `$brand: #ff1f78` как корень проблемы

Это лучше компиляции: находка одна, а не N по числу использований, и чинится в одном месте.

```
token.literal · #ff1f78 · объявлено в _vars.scss:3 как $brand
   используется в 14 местах → чинить надо объявление
   [ Показать все 14 ]
```

Сложные вычисления (`darken($brand, 10%)`, `@each`, циклы) → помечаются как динамика.

### 4.3 Поле `appliedTo`

Критично для правила 3.6. Коллектор должен связать CSS-класс с JSX-элементом, на который он навешен:

```
.field { padding: 11px; }              ← styleValue
<TextField className={styles.field} /> ← jsxElement, resolvedFrom: @sds-eng/base
                                        ⇒ styleValue.appliedTo = "kit:TextField"
```

Без этой связи нельзя отличить «переопределение стилей компонента кита» от «стиль своего div».

### 5.1 Цвет

**Принцип: любой сырой цветовой литерал — находка. Всегда.** Совпадение с токеном влияет только на то, что мы предложим в замену, но не на сам факт находки. `#ff1f78` в коде — это не токен, даже если он в точности равен `pink500`, и даже если он «похож» на токен.

Поэтому правило одно верхнеуровневое, с подвидами — иначе счётчик размазывается по четырём разным правилам и в шапке нет честной цифры.

```

  ├─ shade    ΔE < 0.1, свой оттенок                         18
  └─ foreign  вне палитры                                    14
```


#### `component.novel` — кандидаты в дизайн-систему

Компонент без аналога в ките — **не нарушение**. Это либо законный продуктовый компонент, либо пробел дизайн-системы. Отличить одно от другого можно по тому, насколько он переиспользуется:

```
ранг = использований × log(файлов) × (1 + дублей)
```

| Сигнал | Что означает |
|---|---|
| Использован 1 раз в 1 файле | продуктовая специфика, оставить как есть |
| Использован 23 раза в 8 фичах | сильный кандидат в кит |
| Скопирован в 3 места (MinHash внутри проекта) | **очень** сильный кандидат — команда уже дублирует |
| Состоит только из компонентов кита | композиция — дешёвый кандидат, легко унести |
| Содержит сырые примитивы и хардкоды | сначала нужно причесать |

Отдельный экран дашборда **«Кандидаты в дизайн-систему»** — это выход для команды кита, а не претензия к продуктовой команде. Ранжируется по убыванию ранга, с примером кода и списком мест использования.

Разбор эвристик:

| # | Эвристика | Что ловит |
|---|---|---|
| 1 | **Import-graph** | Объявлен локально, не импортирован из `@sds-eng` → кандидат |
| 2 | **Shadow naming** | `MyButton`, `CustomModal`, `AppDialog` — после снятия префиксов `My/App/Custom/Base/New/V2/Ui/Common/Styled/Wrapped` + словарь синонимов (`Modal ≈ Dialog ≈ Popup`, `Notification ≈ Toast ≈ Snackbar`, `Drawer ≈ SidePanel`, `Chip ≈ Pill ≈ Tag`, `Spinner ≈ Loader`, `TextField ≈ Input`) |
| 3 | **Raw DOM** | `<button>`, `<input>`, `<select>`, `<textarea>`, `<table>`, `<dialog>`, инлайновый `<svg>` |
| 4 | **ARIA/role** | `role=tablist` → Tabs, `role=dialog`/`aria-modal` → Modal, `aria-expanded` + анимация высоты → Accordion, `aria-haspopup=listbox` → Select |
| 5 | **Prop similarity** | Jaccard с `propSignature`, веса TF-IDF: редкие имена (`onClose`, `anchorEl`, `placement`) весят больше, чем `children`/`className` |
| 6 | **Style fingerprint** | Набор CSS-свойств ≈ comp-токенам компонента: `border-radius` + `padding` + `background` + `:hover` + `cursor:pointer` + текст ≈ кнопка |
| 7 | **Clone detection** | Нормализованный AST → MinHash + LSH против исходников кита. Порог > 0.6 → «форк компонента Y, разошлись в N местах» |

Отдельно — **внутрипроектная дедупликация**: тот же MinHash проекта против самого себя находит один и тот же кастом, скопированный в 5 фич. Это аргумент «унести в кит».

### 5.6 Переопределение стилей на компоненте кита

```
className / classes / style / styled(KitComponent) на компоненте кита
        │
        ▼
  какие CSS-свойства внутри?
        │
 ┌──────┼──────────────┬───────────────┬──────────────┐
 │раскладка            │перекраска     │размеры       │
 │margin, width,       │background,    │padding,      │
 │flex, grid-*,        │color, border,  │height        │
 │position, order      │radius, font-* │              │
 ▼                     ▼               ▼              │
 ОК                 warning          info             │
 не находка         «есть варианты   «возможно нужен  │
                     view/token»      другой size»    │
                                                      │
        ├─── целятся в слот с doc.inner === true ─────┤
        │    error «приватный слот, сломается         │
        │           при обновлении кита»              │
        │                                             │
        └─── !important ──────────────────────────────┘
             error «явная борьба с дизайн-системой»
```

Полная таблица политики:

| Что внутри класса | Вердикт | Почему |
|---|---|---|
| `margin`, `width`, `flex`, `grid-*`, `align-self`, `order`, `position` | **ок**, не находка | Позиционирование в родительской раскладке — вне ответственности компонента |
| `background`, `color`, `border`, `border-radius`, `box-shadow`, `font-*` | **warning** | Перекраска. Есть варианты (`view`) или токены |
| `padding` внутри компонента, `height` | **info** | Компонент, вероятно, не подошёл по размеру — возможно, нужен другой `size` |
| Целятся в слот с `@inner` | **error** | Приватная стилизация. Сломается при обновлении кита |
| `!important` | **error** | Явная борьба с дизайн-системой |
| `styled(Button)` с перекраской | **warning**, отдельное правило | Скрытый форк: выглядит как кит, ведёт себя иначе |

**Почему не «любое переопределение — отклонение»:** на реальном проекте ~80% `className` на компонентах — это `margin` и `width`. Отчёт, где 80% находок ложные, не читают.

**Почему не «только `@inner` и `!important`»:** пропустим самое вредное — перекрашивание через публичный `root`-слот. Оно выглядит невинно, а именно оно и разрушает единообразие.

Данные для правила уже есть: `components.json` содержит `slots[].doc.inner` (246 слотов с флагом), коллектор отдаёт список свойств и `appliedTo`.

### 5.7 Классификация обёрток

Компонент импортирует кит — это не обязательно плохо. Четыре подтипа:

| Подтип | Пример | Вердикт |
|---|---|---|
| **Тонкий алиас** | реэкспорт / проброс пропов без изменений | ✅ ок |
| **Обёртка с дефолтами** | фиксирует `view="primary"` | ⚠ info, зафиксировать |
| **Обёртка с переопределением стилей** | `styled(Button)`, `classes={{root}}`, `!important` | 🔴 warning — скрытый кастом |
| **Форк** | скопировали исходник и правят | 🔴 error — см. clone detection |

### 5.8 Позитивная сторона

Отчёт, состоящий только из ошибок, читают один раз. Считаем и хорошее:

| Метрика | Как считается |
|---|---|
| **Adoption** | доля JSX-элементов из кита от всех компонентных элементов |
| **Token coverage** | доля стилевых значений через токены/CSS-переменные от всех значений |
| **Компоненты без замечаний** | ноль отклонений, ноль переопределений |
| **Чистые файлы** | «17 из 94 файлов без единого отклонения» |
| **Топ используемых компонентов** | что реально работает |
| **Health score 0–100** | взвешенная композиция, формула публикуется в отчёте |

Доступность — **грань существующих сущностей, а не параллельная ветка**: те же `Finding`, тот же реестр, та же стадия C. Подробный контракт данных — [`a11y.md`](./a11y.md), обоснование решений — [`a11y-research.md`](./a11y-research.md).

Два правила устроены иначе, чем остальные, и это осознанно:

* **`a11y.lint`** оборачивает канонический `eslint-plugin-jsx-a11y` вместо того, чтобы воспроизводить его 29 правил. Базовый слой доступности — это спека, которая дрейфует, и ручная реализация с ней расходится; в этом же проекте самописный accname дал 11 ложных срабатываний из 11 на первом же реальном коде. Линтер запускается в **сканере** (стадия B), потому что он парсит исходники, а синтаксис живёт ровно в одной стадии; в наблюдения попадает `lintMessages[]` — факт «правило сработало здесь», а суждение о severity и критерии WCAG остаётся в стадии C.
* **`a11y.pattern.*`** сверяются не со спецификацией, а с китом: `kit-a11y.json` фиксирует, что `@v-uik/tabs` обрабатывает четыре стрелки, поэтому находка звучит как «компонент кита `Tabs` это умеет, ваш — нет». Такое утверждение читатель может проверить, и оно приходит вместе с заменой.

**~60–70 % находок закрываются полностью на этом уровне, с готовым кодом замены и без единого токена LLM.** Хардкод цвета, точно равный токену, — самая массовая категория, и она чинится тривиально.

## 6. Схема Finding

Единый формат для всего конвейера.

```ts
interface Finding {
  id: string                      // 'f_0041' — стабильный, для deep-link
  rule: string                    // 'token.color.hardcoded'
  severity: 'error' | 'warning' | 'info'
  confidence: number              // 0–1

  file: string                    // относительный путь
  line: number
  column: number

  snippet: {
    before: string                // ±5 строк контекста
    after: string | null          // null, если фикс неизвестен
    highlightLine: number
  }

  actual: string                  // '#ff1f78'
  expected: {                     // null, если предложить нечего
    token: string | null          // 'sys.Background.backAccent'
    cssVar: string | null         // '--sds-eng-Background-backAccent'
    component: string | null      // 'Modal' — для component.*
    value: string                 // готовая строка замены
  } | null

  why: string                     // человекочитаемое объяснение с последствием
  note: string | null             // предупреждение, напр. про тёмную тему

  /**
   * Грань доступности; `null` на находках, которые её не несут.
   *
   * Вложенный объект, а не три плоских поля: `pattern` бессмысленен на хардкоде цвета, и
   * расширять универсальную схему словарём одного семейства правил — способ превратить
   * контракт в свалку.
   */
  a11y: {
    wcag: string[]                // ['2.1.1'] — критерии успеха; [] если неприменимо
    pattern: string | null        // 'tablist', 'dialog-modal' — роль или паттерн
    impact: string                // что теряет пользователь. Никогда не пустая
    fix: string | null            // что сделать, одним предложением. Не код: см. ниже
  } | null


> `fix` и `expected` — разные вещи, и объединять их нельзя. `expected.value` дашборд
> предлагает скопировать и вставить; `fix` — проза. «Дайте контролу доступное имя» —
> правильный совет, который никакой патч не выражает, потому что имя зависит от того, что
> контрол делает. Проза в `expected.value` уехала бы читателю как код. Дифф есть у четырёх
> проверок из 38 — там, где правка ровно одна: удалить избыточную роль, исправить
> однозначную опечатку, обнулить положительный `tabindex`, снять `autoFocus`.

  autoFixable: boolean            // применимо патчем без ИИ
  needsAgent: boolean             // требует стадии E

  candidates: {                   // только для component.*
    component: string
    score: number
    reasons: string[]
  }[]

  impact: {
    occurrences: number           // сколько раз встречается в проекте
    files: number
  }

  // заполняется стадией E
  enrichment: {
    verdict: 'replaceable' | 'partially' | 'legitimate-custom'
    replacement: string
    propMapping: { from: string; to: string }[]
    manualSteps: string[]
    confidence: number
    verification: { passed: number; total: number }
  } | null
}
```

`impact` нужен для ранжирования: отклонение, встречающееся 40 раз, важнее уникального.

### 7.6 Экран 5 — доступность

**Реализовано:** `dashboard/src/screens/A11y.tsx`, пятый пункт левого меню, горячая клавиша
`5`. Вся логика раскладки — `dashboard/src/lib/a11y.ts`, тесты — `src/report/dashboard-a11y.test.ts`.

Экран **режет те же самые находки**, а не заводит параллельный список: `category === 'a11y'`.
Экраны 1–4 не тронуты: карточка доступности на «Сводке» ведёт туда же, куда вела. Полный
контракт данных — [`a11y.md`](./a11y.md).

| Раздел | Содержимое | Откуда |
|---|---|---|
| Сводка | счётчики по severity, число затронутых критериев WCAG | `findings[].a11y.wcag` |
| **Клавиатура** | виджеты, недостижимые с клавиатуры; подавленный фокус-ринг; диалоги без Escape | `pattern.keyboard`, `pattern.focus`, `focus.suppressed` |
| Базовые правила | сгруппированы **по `subkind`** — это имя правила плагина | `a11y.lint` |
| Имена и семантика | контролы без доступного имени, невалидный ARIA, связи в никуда | `name.missing`, `aria.*`, `pattern.relations` |
| Контраст | пары со swatch'ами и коэффициентом | `contrast.text` |
| **Не проверено** | что осталось за кадром и почему | `limitations[]` |

Три требования, которые легко нарушить:

1. **`a11y.lint` даёт 60–90 % находок**, и все они под одним `rule`. Без группировки по
   `subkind` экран превращается в полсотни одинаковых строк.
2. **Пустой список ≠ «чисто».** Если в `limitations[]` есть `spec-unavailable`, шапка
   обязана сказать, что проверка неполная: молчание рядом с невыполненной проверкой
   читается как одобрение.
3. **`a11y.impact` — в заголовок карточки, `why` — мелким.** Первое говорит, что теряет
   человек; второе объясняет правило. Обратный порядок превращает экран в справочник.

Как это решено на практике:

* Свёртка идёт по `impactKey`, а не по `subkind`. Для `a11y.lint` этот ключ и есть
  `a11y.lint:<правило плагина>`, поэтому требование 1 выполняется само собой — экран не
  обязан знать, что одно правило особенное.
* Раздел, оставшийся пустым при невыполненной проверке, говорит об этом прямо, а не молчит.
* Правило, не попавшее ни в один раздел, показывается в «Прочем», а не исчезает из отчёта —
  та же логика, по которой адаптер линтера сообщает о неклассифицированных правилах.

Фильтр по `wcag` живёт в URL (`?wcag=2.1.1`) и попадает в общую строку фильтров, так что
ссылка на «всё про клавиатуру» вставляется в тикет как есть.

### 7.7 Технический стек дашборда

Дашборд — **полноценное React-приложение, собираемое в один self-contained HTML**. Не генерация HTML строками: при нужном уровне интерактивности (фильтры, виртуализация, 6 уровней проваливания, синхронизация с URL) шаблонизатор превращается в самодельный фреймворк, только хуже.

```
ds-analyzer/dashboard/          ← отдельное Vite-приложение
├── src/
│   ├── components/ui/          ← shadcn/ui (Radix + Tailwind)
│   ├── screens/                ← Overview · Findings · Candidates · Tokens
│   ├── charts/                 ← обёртки над Recharts
│   └── data.ts                 ← читает window.__DS_DATA__
└── vite.config.ts              ← vite-plugin-singlefile

              npm run build
                    ↓
      один dashboard.html со всем внутри
      (JS, CSS, шрифты, иконки — инлайн)
                    ↓
   генератор подставляет JSON в <script id="ds-data">
```

| Задача | Решение | Почему |
|---|---|---|
| Каркас | **Vite + React 18 + TypeScript** | Состояние нетривиальное: фильтры × поиск × drill-down × URL |
| Дизайн-система дашборда | **shadcn/ui** (Radix UI + Tailwind CSS v4) | Современный вид из коробки, доступность от Radix, компоненты копируются внутрь — никакой зависимости от внешнего рантайма |
| Чарты | **Recharts** через `shadcn/ui charts` | Одна библиотека на все графики → консистентность. Темизируется теми же CSS-переменными, что и остальной UI |
| Дифф | **react-diff-viewer-continued** | Side-by-side и unified, посимвольная подсветка внутри строки, темизируется |
| Подсветка синтаксиса | **Shiki**, **на этапе генерации** | 0 КБ рантайма, см. ниже |
| Иконки | **lucide-react** | Родные для shadcn, tree-shaking |
| Виртуализация | **@tanstack/react-virtual** | 1000+ находок без неё тормозят |
| Сборка в один файл | **vite-plugin-singlefile** | Всё инлайнится в один HTML |

Итог: **~1.2–1.8 МБ один HTML-файл**, открывается двойным кликом, без сервера и без сети.

**Ключевой приём — подсветка синтаксиса на этапе генерации.** Shiki с грамматиками весит ~6 МБ, тащить его в браузер бессмысленно. Но подсветка статична: прогоняем в Node при сборке артефакта, в JSON кладём уже готовый размеченный HTML. Ноль байт рантайма, точность как в VS Code.

#### Визуальный язык

Собственный, современный. Основа — токены shadcn/ui, переопределённые под задачу.

```css
:root {
  --background: 0 0% 100%;      --foreground: 240 10% 3.9%;
  --card: 0 0% 100%;            --muted: 240 4.8% 95.9%;
  --border: 240 5.9% 90%;       --radius: 0.65rem;

  /* семантика аудита */
  --severity-error: 0 84% 60%;
  --severity-warn:  38 92% 50%;
  --severity-info:  217 91% 60%;
  --severity-ok:    142 71% 45%;
  --candidate:      271 81% 56%;   /* кандидаты в ДС — не ошибка, свой цвет */
}
.dark { … }
```

Решения по виду:

* **Тёмная тема по умолчанию** — это инструмент разработчика, он открывается рядом с редактором
* **Плотность выше дефолтной shadcn** — на экране должно помещаться много находок; компактный режим переключается
* **Цвет несёт смысл, а не украшает** — severity, и только. Всё остальное — нейтральная шкала
* **Моноширинный шрифт для кода** — JetBrains Mono инлайном (variable, ~80 КБ подмножество)
* **Анимации только функциональные** — раскрытие деталей, переход между уровнями. Никаких декоративных
* **Плавные переходы между уровнями drill-down** — view transitions, чтобы не терять контекст

> Ранее рассматривался вариант стилизовать дашборд токенами самого кита (догфудинг). Отклонено: приоритет — качество и современность интерфейса, а не демонстрация кита.

#### Прочее

* Данные встроены как `<script type="application/json" id="ds-data">`, приложение читает их при старте
* Навигация `?screen=findings&rule=token.literal.color&file=OrderCard.tsx&finding=f_0041` — вся глубина проваливания в URL, ссылкой можно делиться
* Клавиатура: `j`/`k` — по находкам, `/` — командная палитра (shadcn `Command`), `f` — фильтры, `c` — копировать, `?` — справка
* Экспорт: `findings.json`, Markdown-сводка, `.patch` со всеми авто-фиксами
* Дашборд собирается **один раз** при сборке `ds-analyzer`; генератор артефакта только подставляет JSON — то есть анализ проекта не требует ни Vite, ни npm-install

## 8. Стадия E — ИИ-слой

Вызывается **только** для находок с `needsAgent: true` — это ~10–20 % от общего числа.

```
findings.json
     │
     ▼
 фильтр: needsAgent === true         ← ~10–20% находок
     │
     ▼
 ┌───────────────── FAN-OUT ─────────────────┐
 │                                            │
 ▼              ▼              ▼              ▼
агент 1       агент 2       агент 3   …   агент N
OrderDialog   SettingsTabs  MyButton
     │             │             │              │
 вход каждого ≈ 8 000 токенов:
 ├ сниппет с контекстом (±20 строк)      ~500
 ├ T0-каталог кита, 61 строка          ~3 000
 ├ T1-карточки топ-3 кандидатов        ~2 500
 │   пропы + варианты + слоты + 2 примера из examples/
 └ детерминированные reasons             ~200
     │             │             │              │
 выход:  { verdict: replaceable | partially | legitimate-custom,
           component, replacement (JSX),
           propMapping[], manualSteps[], confidence }
     │             │             │              │
     └─────────────┴──────┬──────┴──────────────┘
                          │
                   confidence < 0.75 ?
                          │
                     ┌────┴────┐
                    нет│         │да
                       │         ▼
                       │   ┌──────────────────────────┐
                       │   │ 3 верификатора, разные   │
                       │   │ линзы, задача — ОПРОВЕРГ.│
                       │   │ ├ корректность            │
                       │   │ ├ доступность             │
                       │   │ └ визуальная эквивал-ть   │
                       │   │ проходит при 2 из 3       │
                       │   └────────────┬──────────────┘
                       │                │
                       └────────┬───────┘
                                │
                                ▼
                    enriched-findings.json
                                │
                                ▼
                      агент-синтезатор
                      (видит только сводку, не код)
                      → темы, паттерны, план миграции
                                │
                                ▼
                        dashboard.html
```

### 8.1 Почему плоский fan-out, а не иерархия

Каждый агент независим, контекст маленький, отказ одного не роняет остальных. Финальный синтезатор видит только сводку, а не код — его задача найти повторяющиеся темы («в 12 местах перекрашивают Button через className — возможно, нужен новый вариант в ките»), а не проверять каждую замену.

### 8.2 Состязательная проверка

Для находок с `confidence < 0.75` — три независимых верификатора с **разными линзами**, каждому дана задача **опровергнуть**, а не подтвердить. Проходит при 2 из 3.

Это отсекает правдоподобные, но неверные замены, которые в одиночном проходе выглядят убедительно. Диверсификация линз важнее избыточности: три одинаковых скептика ошибаются одинаково.

### 8.3 Что ИИ-слой делает с результатом

**Только пишет в дашборд + кнопка «скопировать».** Ничего не пишет в файлы проекта.

Замены от LLM не всегда верны; разработчик видит дифф и решает сам. Авто-фиксы (детерминированные, из стадии C) — отдельная история, они идут через `/ds-fix` в виде патча.

```
.claude/
├── skills/
│   ├── ds-audit/SKILL.md      # стадии B + C + D — детерминированно, секунды
```

| **14** | **Субагент `ds-matcher` + скилл `ds-deep`** | Fan-out по `needsAgent`, T0/T1-контекст, `enriched-findings.json`, перегенерация дашборда | Сгенерированный JSX для `OrderDialog` компилируется | L |
| **15** | **Состязательная верификация** | 3 верификатора с разными линзами для `confidence < 0.75` | Заведомо неверная замена отбраковывается | M |
| **16** | **Скилл `ds-fix`** | `.patch` из `autoFixable`, `--dry-run` | `git apply` проходит, demo-app собирается | S |

**Шаги 1–9 дают полностью рабочий продукт без единого токена LLM** — сканер + красивый дашборд с диффами и авто-фиксами. Шаги 10–16 добавляют ИИ там, где он незаменим.

Критический путь до первой демонстрации: **1 → 2 → 3 → 4 → 7 → 8 → 9**. Шаги 5, 6 можно делать параллельно с 7.

### 11.1 Демо-проект как тестовый оракул

Готового проекта на этом ките нет (`packages/showroom` — это Storybook самого кита, не потребитель). Собираем свой `demo-app/`.

Это не только демо. Планируя отклонения **осознанно** и записав `expected-findings.json`, получаем ground truth и можем измерить **precision / recall каждого детектора** — иначе «работает» остаётся мнением.

```
demo-app/
├── src/
│   ├── features/
│   │   ├── orders/      OrderTable(чистый) · OrderDialog(кастом Modal)
│   │   │                OrderCard(хардкод цветов) · OrderFilters(API-нарушения)
│   │   ├── auth/        LoginForm(чистый, эталон) · PasswordField(обёртка со стилями)
│   │   └── settings/    SettingsTabs(кастомные Tabs через role=tablist)
│   ├── shared/
│   │   ├── ui/          MyButton(форк кнопки) · Spinner(инлайновый SVG)
│   │   └── styles/      theme.scss(магические числа)
│   └── App.tsx
└── fixtures/
    └── expected-findings.json    ← 60–80 размеченных вручную ожидаемых находок
```

Планируемый набор отклонений: точные хардкоды цветов, near-miss (ΔE ≈ 0.005), чужие цвета, off-scale радиусы, разъехавшийся типографический кортеж, чужая гарнитура, прямой импорт `@v-uik`, `view="danger"`, `classes={{root}}`, целевой `@inner`-слот, использование `Input` (deprecated), кастомный Modal, кастомные Tabs, форк кнопки, инлайновый SVG, плюс «чистые» файлы для проверки на ложные срабатывания.

Стек: React + TS + Vite, стили тремя способами (SCSS-модули, styled-components, инлайн-`style`) — чтобы проверить все коллекторы.

## 12. Принятые решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Замена для ref-хардкода | sys, если есть; иначе ref + предупреждение + блок «в ките нет роли» | Правило «ref всегда ошибка» породит нечинибельные находки |
| `className` / `classes` на компонентах кита | Разделять по CSS-свойству внутри: раскладка — ок, перекраска — warning, `@inner`/`!important` — error | 80% `className` на реальном проекте — `margin`/`width` |
| Что делает ИИ-слой с результатом | Только дашборд + копирование, ничего не пишет в файлы | Замены от LLM не всегда верны |
| Что считать кастомным компонентом | Не «кастомный ли», а «есть ли эквивалент в ките». Скор = ответ, порога нет | Философский вопрос заменён на проверяемый |
| Компонент без аналога в ките | Не ошибка — категория `component.novel`, отдельный экран «Кандидаты в ДС», ранжирование по переиспользованию | Это вход для роадмапа кита, а не претензия |
| Что считать находкой по токенам | **Любой** сырой литерал, независимо от совпадения. Совпадение влияет только на предложение | «Похож на токен» ≠ «токен». Одна честная цифра в шапке вместо четырёх правил |
| Целевой стек стилей | SCSS-модули основной, CSS-in-JS наравне, Tailwind — плагин | Правилам всё равно, различаются только адаптеры сбора |
| SCSS-переменные | Два прохода: координаты из исходника + разрешение цепочек. Находка на объявлении, а не на 14 использованиях | Компиляция теряет координаты; чинить надо в одном месте |
| Дашборд — как строится | React + Vite, собирается в один HTML через `vite-plugin-singlefile` | Уровень интерактивности такой, что шаблонизатор выродился бы в самодельный фреймворк |
| Дизайн-система дашборда | **shadcn/ui** (Radix + Tailwind v4), тёмная тема по умолчанию | Современный вид, доступность, компоненты копируются внутрь |
| Чарты | Recharts через `shadcn/ui charts` | Одна библиотека на все графики → консистентность и общая темизация |
| Подсветка кода | Shiki **на этапе генерации**, не в рантайме | 0 КБ в бандле, точность VS Code |
| Стилизация дашборда токенами кита | **отклонено** | Приоритет — качество интерфейса, а не демонстрация кита |
| Требования к сканеру | Никаких допущений о структуре проекта. Отдельная стадия B0 определяет корень, алиасы и способ импорта кита | Сканер должен переваривать любой React/TS-проект без настройки |
| Конфиги проекта (vite/webpack) | Разбираем статически, **не выполняем** | Выполнение чужого конфига небезопасно и требует установленных зависимостей |
| Ошибка разбора файла | В `limitations[]`, сканирование продолжается | Молчаливый пропуск читается как «здесь чисто» |
| Демо-проект | Собираем свой, с `expected-findings.json` | Ground truth для метрик precision/recall |

### 12.1 Открытые вопросы

* Нужен ли Tailwind-коллектор — зависит от целевых проектов
* Порог `component.custom` (сейчас 0.6) — калибруется на demo-app
* Формула health score — веса категорий требуют обсуждения
* Нужен ли режим CI (exit code при превышении порога отклонений)
* Стоит ли анализировать соседние пакеты кита (`data-grid` и др.) как часть спеки
