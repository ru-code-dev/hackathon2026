# Бизнес-требования · DS-Analyzer

Документ фиксирует, **зачем** существует продукт, для кого он и по каким критериям
оценивается результат. Как именно он устроен — `system-requirments.md`, `features.md`,
`architecture.md`.

---

## 1. Проблема

Компания развивает дизайн-систему `sds-eng` (UI-кит + токены). Продуктовые команды
подключают её, но со временем накапливается **дрейф**:

- цвета и размеры хардкодятся литералами вместо токенов;
- команды пишут собственные кнопки/диалоги/табы, которые кит уже умеет;
- копии компонентов расходятся с оригиналом и друг с другом;
- иконки тянутся из сторонних пакетов или рисуются инлайном;
- стили кита перекрашиваются снаружи через `!important` и приватные слоты;
- нарушения доступности не видны вообще, пока не придёт аудит.

Стоимость дрейфа: неконсистентный интерфейс, двойная поддержка одинаковых компонентов,
болезненные мажорные обновления кита, риски по доступности, а главное — **никто не может
сказать числом**, насколько проект соответствует дизайн-системе.

Ручное ревью не масштабируется: проект на сотни файлов — дни работы дизайнера и техлида,
результат субъективен и устаревает к следующему спринту.

## 2. Продукт

```
                     ┌──────────────────────────────────────┐
   продуктовый       │              DS-Analyzer             │       результаты
   проект ──────────▶│  движок статического анализа         │──▶ дашборд (1 HTML-файл)
   (любой React/TS,  │  + знания о ките (извлечены          │──▶ план работ с диффами
    без установки)   │    автоматически из его исходников)  │──▶ pull request с фиксами
                     │  + скиллы для Qwen Code              │──▶ кандидаты в ДС
                     └──────────────────────────────────────┘──▶ метрика «здоровье» 0–100
```

Аудит запускается одной командой или голосом («запусти скилл ds-audit») и занимает минуты.

## 3. Целевые пользователи

| Роль | Что получает |
|---|---|
| **Разработчик продукта** | план правок по приоритету, готовые диффы, PR в один клик |
| **Техлид / архитектор** | метрику здоровья, динамику от аудита к аудиту, состав интерфейса |
| **Команда дизайн-системы** | кандидатов в ДС, пробелы токенов, матрицу реального использования компонентов |
| **Дизайнер** | наглядный дашборд: палитра мимо токенов, иконки мимо набора, перекраски |
| **Ответственный за доступность** | все a11y-нарушения с критериями WCAG и советами, честный список «не проверено» |

## 4. Ключевые сценарии

- **UC-1 · Аудит перед релизом.** Разработчик запускает `/ds-audit` на текущем проекте,
  получает дашборд и список решений; автофиксы уходят в PR за один сеанс.
- **UC-2 · Приёмка чужого проекта.** Техлид даёт git-URL — скилл клонирует и анализирует
  репозиторий, к которому у него нет локального чекаута.
- **UC-3 · Массовое исправление токенов.** Сотни литералов → десятки «решений» → выбор
  чекбоксами → один дифф → ветка → PR. Ручной работы — только ревью.
- **UC-4 · Пополнение дизайн-системы.** Команда ДС просматривает `component.novel`
  (переиспользуемые компоненты без аналога в ките) и «пробелы кита» — это готовый
  бэклог развития системы.
- **UC-5 · Замена кастомов на кит.** ИИ-этап (`/ds-deep`) сравнивает кастомный компонент
  с карточками кандидатов из кита и выносит вердикт с планом замены.
- **UC-6 · Контроль доступности.** Экран «Доступность» — нарушения с влиянием на
  пользователя, WCAG-критериями, советами и диффами там, где правка однозначна.
- **UC-7 · Регулярный контроль.** «Здоровье» (формула опубликована) — сравнимый KPI:
  один и тот же код всегда даёт одно и то же число (анализ детерминирован).

## 5. Ценностные требования

| ID | Требование | Мотивировка |
|---|---|---|
| BR-1 | Аудит любого React/TS-проекта **без установки чего-либо в проект** | иначе аудит не запустят: чужой CI, легаси, страх сломать lock-файл |
| BR-2 | Результат — **план решений**, а не поток однотипных ошибок | 118 находок = 30 решений; человек работает с решениями |
| BR-3 | Каждая находка объясняет «**почему** это проблема» и что терять | без «почему» отчёт воспринимается как придирки линтера |
| BR-4 | Автофиксы доводятся **до pull request** в корпоративном контуре (Jenkins) | ценность измеряется слитыми PR, а не списками |
| BR-5 | Отчёт **честный**: всё непроанализированное перечислено поимённо | молчаливый пропуск читается как «здесь чисто» и подрывает доверие |
| BR-6 | Знания о ките извлекаются **автоматически** из его исходников | рукописный каталог устареет к следующему релизу кита |
| BR-7 | Порог входа для конечного пользователя — **клонировать репозиторий и запустить `./install.sh`** | Node ≥ 20 и git; ни npm install, ни сборки |
| BR-8 | Отчёт работает **офлайн**: один HTML-файл без сети и CDN | корпоративный контур, пересылка файлом |
| BR-9 | Движок **переносим на другие дизайн-системы** через слой артефактов | см. `add-new-ds-guide.md` |

## 6. Критерии успеха

- Точность на размеченном оракуле: precision и recall ≥ 0.95 (фактически **1.000/1.000**
  на 105 + 9 ожиданиях).
- **0** ложных срабатываний API-правил на канонических примерах самого кита (684 примера).
- Время аудита среднего проекта — минуты; кита целиком (2378 файлов) — единицы минут.
- Дифф автофиксов принимается `git apply` без ручной доводки.
- Пользовательский путь «клон → install → /ds-audit → дашборд» проходит без документации.

## 7. Ограничения и допущения

- Статический анализ: без запуска проекта, без скриншотов, без пиксельного сравнения.
- Языки: TypeScript/JavaScript (JSX/TSX), стили CSS/SCSS/CSS-in-JS-литералы.
- «Похоже, но перерисовано» для иконок и компонентов статически недоказуемо — такие
  случаи помечаются и передаются ИИ-этапу, а не выдумываются.
- Корпоративный PR-канал — Jenkins generic-webhook-trigger; вебхук зашит константой
  по решению команды (хакатон-компромисс, осознанный).
- Сроки — двухнедельный хакатон; качество ядра (сканер, правила, оракул) приоритетнее
  количества фич.
