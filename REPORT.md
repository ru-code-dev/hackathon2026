### Ключевые инженерные решения

1. **Тема исполняется, а не парсится.** `packages/theme` не имеет ни одного внешнего импорта, поэтому её исходники собираются esbuild'ом и импортируются как `data:`-URL. Это исключает переписывание `calcTheme()` (включая нетривиальное слияние `rgba({ref},0.06)` → `#rrggbbaa`) и, следовательно, исключает расхождение между нашей реализацией и настоящей. Плагин следит за появлением внешнего импорта и **валит** экстракцию, если предпосылка перестала выполняться.
2. **Компоненты разбираются чисто синтаксически.** `node_modules` кита не установлены, тайпчекера нет. Проект ts-morph грузится с `noResolve` и `skipFileDependencyResolution`.
3. **Артефакты детерминированы.** Ни одной временной метки; сортировка по код-юнитам, а не `localeCompare` (он зависит от локали машины). Побайтовая воспроизводимость закреплена тестом — артефакты можно коммитить и диффить между версиями кита.
4. **Артефакт валидирует сам себя** zod-схемой до записи. Схема — источник истины, типы выводятся из неё.
5. **Пробелы фиксируются явно.** `typeCheckerAvailable: false`, `externalReExports[].resolved: false`, коды `external-reexport-unresolved` / `props-type-not-found`. Молча вернуть пустой список хуже, чем сказать «неизвестно».

## 2. Дефекты, найденные в самом ките

Экстракция — попутный аудит. Ниже — то, что стоит починить в ките независимо от нашего анализатора.

### 2.1 🔴 Токен вычисляется в `NaN`

`packages/theme/src/theme/textField.ts:46`

```ts
widthShadowFocus: -THEME_TEMPLATES.edsSys.borderWidth.none,
```

Унарный минус применён к строке-шаблону `'{edsSys.borderWidth.none}'`. Результат — `NaN`, он доезжает до потребителя в объекте темы и отбрасывается браузером как невалидное CSS-значение. Проявляется как `comp.input.widthShadowFocus` (файл `textField.ts`, но экспортируемая константа — `input`).

**Починка:** убрать минус либо вычислять на разрешённом значении, а не на шаблоне.

### 2.2 🟡 25 comp-токенов захардкожены в обход тем

Значение записано литералом, а не ссылкой на `sys`/`ref`, поэтому при смене темы или бренд-палитры они не изменятся. Примеры: `comp.bar.colorBorderShadowDark`, `comp.barButton.colorShadowDarkFocus`, `comp.barDivider.colorBackgroundDarkMajor`.

Полный список — `diagnostics[code=comp-token-literal]` в `tokens.json`.

### 2.3 🟡 44 семантических цвета одинаковы в светлой и тёмной теме

Для семейств `*Const` (`BackgroundConst`, `ForegroundConst`) это намеренно. Для остальных — вероятный пробел тёмной темы: `sys.Background.backInfoDarkRed`, `sys.Background.backInfoGrey`, `sys.Background.backInfoViolet` и др.

`diagnostics[code=sys-color-theme-invariant]`.

### 2.4 🟡 Опечатка в JSDoc-теге

`packages/base/src/components/Tag/constants.ts` — `@depreated` вместо `@deprecated`. Любой инструмент, читающий стандартный тег (IDE, документация, линтеры), считает устаревший размер `lg` актуальным API. Наш экстрактор распознаёт обе формы, но чинить надо в ките.

### 2.5 🟠 Отсутствует шкала отступов — самое важное следствие

Тир `ref` содержит только `palette`, `a`, `Switch`, `fontFamilies`, `lineHeights`, `fontWeights`, `fontSize`, `letterSpacing`, `paragraphSpacing`, `textCase`, `textDecoration`, `borderRadius`, `borderWidth`.

Токенов отступов **нет**: padding, margin и gap живут внутри реализаций компонентов (в `@v-uik`).

Прямое следствие для будущего анализатора: правило «кастомный padding» **нельзя** сформулировать как «значение вне шкалы» — сравнивать не с чем. Придётся использовать более слабую эвристику: частотный анализ по проекту (значение, встречающееся 1–2 раза на фоне доминирующих 4/8/12/16, подозрительно) плюс `scales.allDimensionPx` как приблизительный ориентир.

Это не пропуск экстрактора, а свойство кита, и артефакт сообщает о нём явно (`spacing-scale-missing`), чтобы никто не построил правило на несуществующем основании.

### 2.6 ℹ️ Прочее

* `_DNU_ST_` («do not use») реэкспортируется из публичной бочки — любой импорт оттуда является нарушением по собственному именованию кита.
* `Dropdown` и `Labelled` — директории без `index.ts`.
* `Container`, `Dropdown`, `Grid`, `Labelled` существуют на диске, но не экспортированы из `components/index.ts` напрямую (идут через `@v-uik`).
* 2 ключа comp-токенов не ложатся на соглашение об именовании: `comp.backwardCompatibilityMode`, `comp.rating.ccolorTextSelectedActive` (последнее — опечатка, `ccolor`).

## 3. Что ещё можно извлечь сверх текущего объёма

Ниже — инвентаризация того, что в ките есть, но в текущую версию артефактов не вошло. Отсортировано по отношению «ценность для детекции отклонений / трудоёмкость».

### 3.1 🔥 Каталог иконок — 466 SVG

`packages/base/src/icons/svg/` содержит **466** иконок (`io16-*`, `io24-*` и т. д.), импортируемых скриптом `import-icons` в компоненты.

**Зачем:** одно из самых частых и самых заметных отклонений — инлайновый `<svg>` в продуктовом коде вместо иконки кита. Имея каталог (имя, размерный вариант, а лучше — нормализованный хеш `path`-данных), детектор отвечает не просто «здесь инлайновый SVG», а «здесь инлайновый SVG, идентичный `io16-Default` — замените на компонент кита». Это превращает шумное правило в actionable-находку.

**Трудоёмкость:** низкая. Обход директории + парсинг `viewBox`/`path`, плюс нормализация геометрии для сравнения.

### 3.2 🔥 API-документация из MDX — 84 файла

`*API.mdx` / `*Api.mdx` / `api.mdx` содержат таблицы пропов, **которые в исходниках не выводятся**, потому что типы приходят из `@v-uik`.

**Зачем:** это единственный доступный без установки зависимостей источник по пропам компонентов вроде `Radio`, `Slider`, `Splitter` — тех самых, что сейчас помечены `props-type-not-found`. Закрывает главный пробел артефакта компонентов «дёшево».

**Трудоёмкость:** средняя. MDX-таблицы полуструктурированы; нужен парсер + сверка с тем, что уже извлечено из исходников (расхождения сами по себе — находка: документация разошлась с кодом).

### 3.3 🔥 Установить зависимости кита и разрезолвить `@v-uik`

25 пакетов реэкспортируются звёздочкой; их экспорты сейчас неизвестны, поэтому `publicSymbols` (462) — **нижняя граница** публичного API.

**Зачем:** закрывает разом три диагностики (`external-reexport-unresolved`, `props-type-not-found`, `symbol-kind-unresolved`) и делает возможной полноценную валидацию пропов через тайпчекер.

**Трудоёмкость:** низкая по коду, но требует доступа к приватному реестру GitVerse. Контракты уже предусматривают этот сценарий: `meta.typeCheckerAvailable` и `externalReExports[].resolved` станут `true`, форма артефакта не изменится.

### 3.4 🔥 Соседние пакеты — `data-grid`, `rich-textarea`, `tree-dnd`, `browser-tabs`

`data-grid` — 119 файлов, крупный компонент со своей моделью. Остальные меньше (27 / 10 / 6).

**Зачем:** это тоже кит. Проект, использующий `DataGrid`, сейчас анализировался бы вслепую.

**Трудоёмкость:** низкая — экстрактор компонентов параметризуется путём; нужно расширить `config.ts` списком пакетов и добавить в артефакт измерение «пакет».

### 3.5 ⭐ Визуальные снапшоты — 4205 PNG

`__tests__/*-snapshots/` содержит **4205** скриншотов Playwright по трём браузерам.

**Зачем два разных применения:**
1. *Метрика доверия.* Число снапшотов на компонент показывает, насколько жёстко зафиксирован его рендер, а значит — насколько уверенно можно называть отклонением его переопределение (сейчас извлекается только счётчик; `Button` — 594).
2. *Извлечение фактических стилей.* Из скриншотов можно снять реальные цвета и геометрию компонента в каждом состоянии — то, что в токенах не записано (в первую очередь **отступы**, см. §2.5). Это способ построить недостающую spacing-шкалу эмпирически.

**Трудоёмкость:** первое — сделано; второе — высокая (нужен разбор изображений или, лучше, прогон компонентов в headless-браузере с чтением `getComputedStyle`).

### 3.6 ⭐ Вычисленные стили компонентов в рантайме

Радикальное решение проблемы отсутствующих spacing-токенов: отрендерить каждый компонент кита в каждом варианте (варианты у нас уже есть — 38 наборов) в headless-браузере и снять `getComputedStyle` со всех слотов.

**Зачем:** даёт **фактический** контракт — какой padding у `Button size="md"`, какой gap у `Card`. Это именно та информация, которой нет в токенах и которая нужна, чтобы отличить «кастомный отступ» от «отступ как в ките».

**Трудоёмкость:** высокая (нужны установленные зависимости + сборка + Playwright), ценность — тоже высокая. Инфраструктура в ките уже есть: `playwright-ct.config.ts` и компонентные тесты.

### 3.7 ⭐ Хуки — 22 задокументированных

`packages/base/src/hooks/` содержит `.mdx`-документацию на `useClassList`, `useMergedRefs`, `useDebounce`, `useMediaQuery`, `usePopper`, `useOutsideClick` и др. Реализации приходят из `@v-uik/hooks`.

**Зачем:** самописный `useDebounce` в проекте — то же самое отклонение, что самописная кнопка, только менее заметное. Кроме того, имена хуков нужны, чтобы детектор компонентов не принимал их за компоненты.

**Трудоёмкость:** низкая.

### 3.8 ⭐ Глобальные константы `shared/`

`packages/base/src/shared/constants.ts` объявляет общекитовый `sizes = { xs: 'sm', sm: 'md', md: 'lg' }` и `defaultModifiers` для поповеров.

**Зачем:** это кросс-компонентный контракт размеров. Сейчас извлекаются только per-component `constants.ts`; глобальный слой стоит выделить отдельно, чтобы правило «размер вне контракта» работало и для компонентов без собственного `constants.ts`.

**Трудоёмкость:** низкая.

### 3.9 ◦ Брейкпоинты

`createCssVariables.ts` эмитит `--sds-eng-breakpoints-*`, но берёт значения из `createTheme()` пакета `@v-uik/base`, а не из `@sds-eng/theme`. Без установленных зависимостей недоступны.

**Зачем:** детекция кастомных медиазапросов. **Трудоёмкость:** тривиальная после §3.3.

### 3.10 ◦ История версий и миграции

`CHANGELOG.md` в корне и в `packages/base` фиксирует, когда API менялось. Git-история даёт то же в более гранулярном виде.

**Зачем:** отчёт вида «проект использует API уровня 1.1, в 1.3 переименовано X» — это уже не аудит, а план миграции. **Трудоёмкость:** средняя, ценность зависит от целей.

### 3.11 ◦ Storybook-примеры как калибровочный корпус

Сейчас извлекается только инвентарь (имена файлов, счётчики). Само содержимое `examples/` и `*.stories.tsx` — это **заведомо корректное использование кита**.

**Зачем:** дешёвый регресс-тест на ложные срабатывания будущего анализатора: детектор, который срабатывает на сторисах самого кита, откалиброван неверно. Прогонять анализатор по ним в CI — обязательный шаг перед выкаткой правил.

**Трудоёмкость:** низкая, но осмысленна только после появления анализатора.

### 3.12 ◦ Граф зависимостей компонентов кита

Из уже собранных импортов можно построить «`Select` использует `Popover`, `List`, `Icon`».

**Зачем:** ранжирование находок по радиусу поражения (отклонение в компоненте, от которого зависят 12 других, важнее) и поиск циклов. **Трудоёмкость:** низкая — данные уже собраны в `externalDependencies`, нужно добавить локальные рёбра.

## 4. Приоритеты на следующий шаг

Если цель — как можно скорее получить работающий анализатор проектов:

1. **§3.3 — установить зависимости кита.** Разблокирует пропы, брейкпоинты и полный список публичных символов. Наименьшее усилие с наибольшим эффектом на полноту.
2. **§3.1 — каталог иконок.** Дёшево, а инлайновые SVG — массовая и легко чинимая категория отклонений.
3. **§3.4 — соседние пакеты.** Без `data-grid` анализ проектов будет с дырой.
4. **§3.6 — вычисленные стили в рантайме.** Единственный способ закрыть проблему отсутствующей spacing-шкалы (§2.5); имеет смысл начинать после первых трёх.

Всё перечисленное расширяет артефакты **без изменения контрактов** — схемы уже содержат нужные поля и флаги полноты.

## 5. Как воспроизвести

```bash
cd ds-analyzer
npm install
npm run extract     # → artifacts/tokens.json, components.json, extraction-summary.json
npm run verify      # typecheck + lint + 254 теста
```

Установка зависимостей самого кита не требуется.
